# 0067. 本人が ssh で記憶を自分でコミットする

- Date: 2026-10-04
- Status: Accepted（整理係のコミットが失敗したときに捨てる範囲が一晩から工程ごとになることは [ADR 0068](0068-a-curator-that-remembers-like-a-person.md) で改める）

## Context

記憶をコミットするのはサーバーだけである（[ADR 0018](0018-memory-in-git-and-the-nightly-rebuild.md)）。
ターンの終わりに、サーバーは作業ツリーの変更をファイルごとに検査し、当たったものを直前のコミットの状態に戻してから、残りをコミットする。
作業環境（`natsumi-workspace`）には `.git` を読み取り専用で重ね、履歴をなつみの手の届かないところに置いている。

Kubernetes の構成では、本人が ssh で入る口がある（[ADR 0033](0033-running-on-kubernetes.md)）。
本人は作業環境と記憶の領域を読み書きできるが、記憶の `.git` は読み取り専用で、直した分はサーバーが次の区切りでコミットする、と決めていた。

この形では、本人が直したいものを直せない。

- 本人が `always.md`・`personality.md` を直すと、サーバーは次のターンの終わりに、それを日中のなつみの書き込みとして検査する。
  日中は書けないファイルなので、直前のコミットの状態に戻される。
- `INDEX.md` は整理係だけが書くファイルなので（[ADR 0055](0055-a-memory-curator-at-night.md)）、本人が直しても同じく戻される。
- サーバーには、誰が作業ツリーを書いたかを見分ける手段がない。本人の変更も、なつみの変更として扱われる。

本人の変更は、なつみの書き込みを守るための検査の対象にすべきではない。
ADR 0018 も、記憶のリポジトリは本人が自分の git で扱い、手で直すものだとしている。
[ADR 0020](0020-limits-at-write-time-and-a-nightly-menu.md) は、本人が自分の git で直接コミットした `always.md` が上限を超えていても、そのまま prompt に入ることを受け入れている。
Docker（compose）の構成では、本人は data directory の記憶を、コンテナの外から自分の git で直接コミットできる。
Kubernetes の構成だけが、それをできない形になっていた。

二つの案を考えた。

- サーバーに、本人の書き手としてコミットさせる。本人がサーバーに頼み、サーバーが検査を飛ばして本人の名前でコミットする。
  git を書くのはサーバーだけという形は保てるが、natsumi のコードの変更とリリースが要る。
- 本人の ssh の口で `.git` を書けるようにし、本人が自分でコミットする。コミットそのもののためには、natsumi のコードを変えなくてよい。

本人は後者を選んだ。ただし `.git` を書けるようにすると、後で述べるとおり、サーバーの git にコマンドを動かさせる道ができる。
それを塞ぐために、サーバーの git の呼び方を 1 か所変える。

## Decision

- **本人が ssh で入る口では、記憶の `.git` を書けるようにする。本人は記憶を自分の git でコミットしてよい。**
  ADR 0033 の「記憶の `.git` は読み取り専用にする。直した分は、サーバーが次の区切りでコミットする」を、ssh の口について置き換える。
- **作業環境は今までどおりである。** なつみ（`natsumi-workspace`）には `.git` を読み取り専用で重ねたままにし、なつみはコミットできない。
  ADR 0018 の「履歴はモデルの手の届かないところに置く」は変わらない。
- 本人のコミットは、サーバーの検査を通らない。サーバーが検査するのは、自分がコミットするときの作業ツリーの変更だけである。
  本人がコミットした後の作業ツリーは clean なので、サーバーはその変更を見ない。
- コミットしないまま ssh で直したファイルは、今までどおり次のターンの終わりに、なつみの変更として検査される。
  本人の変更を検査の外に置くのは、本人がコミットしたときだけである。
- Docker（compose）の構成は変えない。本人はすでに、data directory の記憶をコンテナの外から自分の git でコミットできる。考え方は同じである。
- ssh の口のマウントと権限の変更は、環境の設定（private のリポジトリ）で行う。

### `.git` を書けるようにする条件

サーバーの git は hook を動かさず（`core.hooksPath` を空にして呼ぶ）、ユーザーとシステムの git の設定も読まない。
ただし、リポジトリの中の設定は読む。そこには `core.fsmonitor` のように、git がコマンドを動かす設定を書ける。
`.git` を書けるようにした口から、そうした設定を置けると、サーバーの UID でコマンドが動く。
サーバーの UID は SQLite・秘密・外のエージェントを呼ぶ token に届く。
これを塞ぐために、次の 3 つをすべて条件とする。どれかが欠けたら、ssh の口の `.git` を書けるようにしない。

1. **ssh の口では、`.git/config` を読み取り専用で重ねてマウントする。** `.git` の他の中身（オブジェクト、refs、index）は書けるので、コミットはできる。
   config を書き換えられないので、コマンドを動かす設定は置けない。
   `.gitattributes` や `.git/info/attributes` の filter も、中身の定義が config に要るので動かない。
2. **ssh の口では、`.git` を独立したマウントにする。** マウントの位置は改名できない。
   独立していないと、`.git` ごと改名して、config を書ける新しい `.git` にすり替えられる。
3. **サーバーの git は、git ディレクトリと共通ディレクトリを環境変数（`GIT_DIR`・`GIT_COMMON_DIR`）で明示して呼ぶ。**
   `.git` の中に `commondir` というファイルを置くと、git は別のディレクトリを共通ディレクトリとして扱い、その config を読む。
   `.git` 自体はロックファイルを作るために書けなければならないので、`commondir` を置くことは止められない。
   環境変数で明示すると、git は config を読むときに `commondir` を辿らない。
   `/sources` の履歴（[ADR 0050](0050-telling-of-source-updates-with-one-event.md)）も同じ呼び方の関数を通るので、同じ扱いにする。作業環境からは読み取り専用なので、こちらは念のためである。

案 B として、サーバーの git の呼び出しで、コマンドを動かす設定（`core.fsmonitor` など）を一つずつ打ち消す形も考えた。
`commondir` の先の config に対しても効く。
しかし、git が版を上げるたびに増えるかもしれない設定を漏れなく挙げ続ける必要がある。一つ漏れれば穴になり、漏れたことに気づく手段も無い。
config を書けなくする形なら、何を書かれ得るかを数えずに済むので、こちらを採った。

### 本人が守ること

- 検査の条件は本人が自分で守る。`.md` だけ、空にしない、1 ファイルの上限、`always.md` の上限、日本語以外の文字を入れない、などである。
  守らなくてもコミットは止まらない。
- 自分が直したファイルだけをコミットする。作業ツリー全体を取り込む形（`git add -A` や `git commit -a`）は使わない。
  ターンの途中や夜の整理係の途中には、まだ検査していないなつみや係の書き込みが作業ツリーにある。
  それを本人のコミットに取り込むと、検査を通らずに履歴に入る。
- ssh でログインするユーザーの umask は 007 のままにする（ADR 0033）。
  本人の git が作るオブジェクトや index をサーバーが書けなくなると、サーバーのコミットが失敗し続ける。

## Consequences

- 本人は `always.md`・`personality.md`・`INDEX.md` を含め、記憶のどのファイルも自分で直して残せる。
  サーバーに戻されることはない。
- 本人のコミットは検査を通らないので、検査に当たる内容も履歴に入り得る。
  そのファイルをなつみが後で書き換えると、書き換えた結果が検査に当たれば、本人のコミットの状態に戻る。
  たとえば本人が 1 ファイルの上限を超えるファイルをコミットすると、なつみはそのファイルを、上限の中に縮めない限り書き換えられない。
- `always.md` と `personality.md` が prompt に入るのは、session を作るときだけである。サーバーは session を作るときに、作業ツリーからこの二つを読む。
  本人がコミットした変更がなつみの prompt に入るのは、次の夜の切り替えか、サーバーの再起動の後からになる。走っている session には入らない。
  ADR 0018 が「差し替えられない場合」として書いた形である。走っている session の instructions は、prefix のキャッシュを守るために差し替えない。
- 夜には、本人が直したものが書き換えられ得る。
  `always.md` と `personality.md` は夜のなつみが見直してよいファイルであり、`INDEX.md` は整理係が毎晩書き直す。
  本人は差分で見て、気に入らなければまた直す。整理係は `always.md` と `personality.md` を変えない（ADR 0055 のまま）。
- 作業ツリーが clean なら、サーバーは何もコミットしない。本人がコミットした直後のターンは、なつみの変更が無ければコミットを作らない。
- 本人のコミットとサーバーのコミットが重なると、git の index のロック（`index.lock`）で片方が失敗する。
  - 本人の側が失敗したら、本人がやり直す。
  - サーバーの側が失敗しても、ターンは壊れない。サーバーはコミットの失敗をログに残すだけで、ターンを続け、変更は作業ツリーに残る。
    次に記憶が変わったターンの終わりに、検査してコミットする。
    検査で戻したファイルの知らせは、そのコミットが失敗した回は、なつみに届かないことがある。
  - サーバーの作業ツリーの状態の確認は、index のロックを取らない設定で git を呼んでいる。ぶつかるのは、戻す・取り込む・コミットするときだけである。
  - 夜の整理係のコミットが失敗すると、係のその夜の変更は全部捨てられる（ADR 0055 の全部か無しかのまま）。
    捨てるときは作業ツリーを最後のコミットにそろえるので、そのときに本人がコミットしていない変更も消える。
    夜の切り替えの間に ssh で直すなら、その場でコミットしておく。
- 整理係は、作業ツリーが clean なときにしか始まらない（ADR 0055）。本人が直したままコミットしていないと、その夜の整理は飛ばされる。
  本人がコミットしておけば、この理由で飛ばされることはない。
- ssh の鍵を持つ人も、上の 3 つの条件がそろっていれば、サーバーの git にコマンドを動かさせることはできない。
  ADR 0033 の「鍵を失うか漏らすと、作業環境と記憶を読み書きされる。SQLite と秘密には届かない」は、この条件のもとで保つ。
  条件はコード（3）と環境の設定（1・2）に分かれている。環境の設定から 1 か 2 が外れると、黙ってこの前提が崩れる。
- 残るリスク。
  - 知らない道。`.git` の中で、config を経ずにコマンドの実行につながる場所が他に無いことは、確かめた範囲でしか言えない。
    確かめたのは、`commondir`、`config.worktree`（`extensions.worktreeConfig` が config に無いと読まれない）、
    `info/attributes`（filter の定義が config に要る）、`objects/info/alternates`（オブジェクトを読む場所が増えるだけ）、hook（無効にして呼んでいる）である。
    git の新しい版で、`.git` の中の新しいファイルが読まれるようになることもあり得る。
  - `objects/info/alternates` で、別の場所のオブジェクトを読ませられる。コマンドは動かないが、大きな置き場を指してサーバーの git を重くできる。
  - git は refs の置き場を探すときには、環境変数にかかわらず `commondir` を辿る（git 2.43 で確かめた）。
    `commondir` を置かれると、サーバーのコミットで動くブランチが別の場所のものになり得る。
    ただし ssh の口からは refs をもともと直接書けるので、これで新しくできることは無い。履歴を壊すことは、`.git` を書ける口に元から伴う。
  - 本番の git の版を上げたら、`commondir` の扱いをテストで確かめ直す。
- 本人の git がサーバーの UID の持つリポジトリを扱うので、ssh の側でも git の `safe.directory` の設定が要る。環境の設定で行う。
- サーバーの git の呼び方を変えるので、natsumi のリリースが要る。ssh の口の `.git` を書けるようにするのは、その版を動かしてからにする。
- git を書く者が二人になる。どちらが書いたかは、コミットの author で見分ける。

### 置き換える既存の決定

- ADR 0033
  - 置き換え: Pod の構成のうち、sshd について「記憶の `.git` は読み取り専用にする。直した分は、サーバーが次の区切りでコミットする」。
    ssh の口では `.git` を書けるようにし、本人が自分でコミットしてよい。コミットしないまま直した分は、今までどおりサーバーが次の区切りで検査してコミットする。
  - 条件づけ: Consequences の「SQLite と秘密には届かない」。ssh の口の `.git` を書けるようにしたあとは、上の 3 つの条件がそろっている間だけ成り立つ。
  - 残す: 作業環境の `.git` は読み取り専用であること。sshd を外から直接つなげる口で公開し、門を ssh の鍵だけとすること。UID と共有のグループの形。
- ADR 0018
  - 具体化:「記憶のリポジトリは、オーナーが自分の git で pull・push し、手で直すものである」。本人が自分でコミットした変更は、サーバーの検査の対象にしない。
  - 残す: サーバーが検査してコミットするのは、ターンの終わりの作業ツリーの変更であること。`natsumi-tools` に git を入れず、作業環境の `.git` を読み取り専用で重ねること。
