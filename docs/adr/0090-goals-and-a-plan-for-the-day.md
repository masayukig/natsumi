# 0090. 目標を記憶の `goals/` に置き、ping は今日の計画を進める合図にする

- Date: 2026-10-31
- Status: Accepted

## Context

[ADR 0014](0014-self-checks-and-pings.md) で、起きている時間帯の静かな時間ごとに、合図 `ping` を思考ループに入れるようにした。
「何かしたいことは？」という意味で、何もなければなつみはそのまま終える。

本人は「ping であまり何もしていない」と感じた。本番の記録で確かめると、そのとおりだった。

- ping は 1 日に 25〜30 回ほど届いていた。1 週間で、なつみが返事や知らせを出した ping は 1 回も無かった。
- ツールを呼んだ ping のターンは、1 週間で 1 回だけだった。ほかはモデルを 1 回呼んで、そのまま終わっていた。
- ping の出来事に載るのは、今の時刻（`local_time`）と、本人がまだ確かめていない知らせの件数だけである。
  system prompt の ping の説明は「なければ何もせずに終えます」で終わる。
  ping のターンには、何をするかの手がかりが無い。

なつみが何のためにいるか（目的）と性格は、記憶の `personality.md` と `always.md` にある（[ADR 0018](0018-memory-in-git-and-the-nightly-rebuild.md)）。
どちらも system prompt に入り、夜の振り返りでだけ書き換えられる。
インスタンスによっては、続けて見守りたいことを `always.md`、マニュアル、繰り返しの予約（[ADR 0063](0063-repeating-self-checks-without-limits.md)）に分けて書いていた。
どれも「今日は何をするか」を決める材料としては、まとまっていない。

ほかの製品では、本人の目標を受けて行動計画を立て、進み具合を追い、途中で手を出せる仕事を自分から引き受ける形がある。
これを参考に、なつみに目標のファイル（goals）を持たせることにした。
設計は本人と grill-me（Q1〜Q9）で詰めた。

満たしたい制約は次のとおりである。

- バックエンドは prefill が遅い。system prompt とツールの説明は prefix cache に乗せたい（[ADR 0019](0019-a-workspace-not-a-memory-tool.md)・[ADR 0020](0020-limits-at-write-time-and-a-nightly-menu.md)）。
- 本人は、SQLite にデータをあまり持たせたくない。テキスト（Markdown）でよい。
- 夜の仕事は、すでに上限ぎりぎりで回している（ADR 0020・[ADR 0068](0068-a-curator-that-remembers-like-a-person.md)）。増やさない。
- 長く続く目標が、なつみの書き込みで勝手にずれないようにしたい。

## Decision

### 層: 目的は今の場所に残し、goals は長く続く目標・日課・短い目標を持つ

3 つに分ける。

| 層 | 中身 | 置き場所 |
| --- | --- | --- |
| 目的 | なつみが何のためにいるか。本人が決め、めったに変わらない | 今までどおり `personality.md`・`always.md` |
| 長く続く目標 | 終わりの無い目標。例「クラスタを健康に保つ」 | goals |
| 短い目標 | 終わりの条件か期限がある目標。長く続く目標のどれかにつながる | goals |

- goals には、長く続く目標ごとに、日課（毎日やること）と、日々の状態（今の様子）も持たせる。
- 日課は時刻を決めない仕事である。時刻が大事な定期の仕事は、今までどおり繰り返しの予約（ADR 0063）に残す。

退けた案:

- **長く続く目標を `always.md` に書く**: 目標が勝手にずれない点は良い。
  しかし、目標ごとの今の様子を置く場所が無い。`always.md` は夜にしか書けず、日中の進み具合を書き込めない。
  ずれない点は、文言を誰が変えられるかで保つ（後の節）。

### 置き場所: 記憶の `goals/` に、長く続く目標ごとに 1 ファイルと、今日の計画

- 記憶のリポジトリの直下に `goals/` を置く。サーバーが名前を決めるディレクトリになる（`postbox/` と同じ。[ADR 0076](0076-a-postbox-for-requests-sent-on-a-schedule.md)）。
- 長く続く目標ごとに、Markdown のファイルを 1 つ置く。ファイル名が目標の ID である（`goals/cluster-health.md` など）。
- 1 つのファイルの節は次の 4 つである。

| 節 | 中身 | 書けるのは |
| --- | --- | --- |
| なぜ | 長く続く目標の文言 | 本人の同意の後に、なつみ |
| 日課 | 毎日やること（時刻は決めない） | 本人の同意の後に、なつみ |
| 今の様子 | 最後に見た日と、そのときの様子 | なつみが自由に |
| 短い目標 | この目標につながる短い目標と、その進み具合 | なつみが自由に |

- 日課と短い目標は、つながる長く続く目標のファイルの中に書く。日課と短い目標に「何のため」が付く。
  どの目標にもつながらない日課が出てきたら、長く続く目標を足すことを本人に持ちかける合図とする。
- 今日の計画は `goals/today.md` である。先頭に日付を書く。なつみが自由に書き換えてよい。
- `goals/` の下にサブディレクトリは作らない。長く続く目標のファイルは `goals/` の直下の `.md` のうち、`today.md` 以外のすべてである。
- ファイルの書き方（節の見出し、日付の書き方、計画の立て方）は、マニュアル `manual/goals.md` に書く。system prompt には書かない。

退けた案:

- **1 つのファイルに全部の目標を書く**: 目標の作成と削除が git の差分で目立たない。長さの上限もファイルごとに掛けられない。
- **長く続く目標と、日課・短い目標をファイルで分ける**: 日課と短い目標から「何のため」が離れる。

### 本人の同意が要るものと、なつみが自由に書くもの

- 本人の同意が要るのは、長く続く目標の作成・削除・文言（「なぜ」の節）と、日課（「日課」の節）である。
  - なつみが持ちかけ、本人がうなずいたら、なつみが書く。足す、消す、言い換える、のどれも同じである。
- なつみが自由に書くのは、「今の様子」、「短い目標」、`today.md` である。
- 本人は、いつでも ssh で直接直してよい（[ADR 0067](0067-the-owner-commits-memory-over-ssh.md)）。

### 同意の要る部分の変更は拒まず、ダッシュボードに出す

- 同意の要る部分の変更を、サーバーは拒まない。検査で拒むと、本人がうなずいた後に、なつみが書けなくなる。
- 代わりに、ダッシュボード（[ADR 0049](0049-a-read-only-dashboard-in-the-browser.md)）に、同意の要る部分の変更の一覧を出す。
  - 載せるのは、長く続く目標のファイルの作成と削除、「なぜ」と「日課」の節の変更である。コミットの時刻と書き手、差分を並べる。
  - 一覧は、記憶のリポジトリの git の履歴から作る。SQLite には持たない。
  - 本人は、なつみを通して聞かなくても、何が変わったかを見られる。

退けた案:

- **次のターンに差分を添えて、なつみから本人に伝えさせる**: 本人は、毎回なつみを通して聞きたくない。
- **サーバーが本人に直接知らせる**: 本人に届くのはなつみの言葉だけ、という形（[ADR 0008](0008-single-thinking-loop-and-mac-conversation.md)）を崩す。
- **検査で拒む**: 上のとおり、同意の後に書けなくなる。

### 計画: 日付が変わって最初の ping で、goals から今日の計画を立てる

- 日付（`loop.timeZone` の日付）が変わって最初の ping で、なつみは goals から `today.md` を立て直す。
  - 日課は必ず計画に入れる。
  - 済んだ短い目標は、このとき消す。経緯は git に残る。
  - 長く続く目標と短い目標を見渡すのは、このときだけである。
- 計画は日中も書き換えてよい。本人に頼まれたことを足す、済んだものに印を付ける、などである。
- 夜の振り返りと記憶の整理係には、計画の仕事を足さない。

退けた案:

- **夜の振り返りで、翌日の計画を引き継ぎに書く**: 日中に書き換えたい。引き継ぎは session の system prompt に入るので、日中に変えても効かない。

### ping: 固定の説明で、計画に沿って進めさせる

- system prompt の ping の説明を、固定の文に書き換える。設定や記憶から組み立てない。変わるのは、この ADR を入れた版の最初の session だけである。
- 説明で求めることは次のとおりである。正確な文は実装の PR で決める。
  1. `today.md` の日付が今日でなければ、goals から計画を立て直す（前の節）。
  2. 計画に沿って進める。済んだら、計画と、つながる目標の「今の様子」・「短い目標」を更新する。
  3. 計画が済んでいたら、長く続く目標を見直す。今日のうちにできる短い目標があれば、計画に足して進める。無ければ、何もせずに終える。
  4. 長く続く目標が 1 つも無ければ、目標と日課の案を作り、本人に持ちかける（後の「最初の goals」の節）。
  5. 本人に伝えたいことや確かめてほしいことがあれば、今までどおり `reply_to_mac`・`notify_owner` を使う。
- 本人に話しかけるかどうかは、今までどおりなつみが決める。

退けた案:

- **ping のたびに、サーバーが長く続く目標を 1 つ選んで載せる**（SQLite か git の履歴で順に回す）:
  本人は、ping のたびに違う目標をやらせるのは違うと考えた。毎回目標を載せると、履歴に 1 日 2〜3 万 token が積もる。
- **計画が済んだ後、長く続く目標に役立つことを自分で探してやらせる**: 作業と記憶が膨らむ。今日できる短い目標を足すところまでにする。

### ping に載せる今日の計画: session の最初と、compaction の後の最初だけ

- サーバーは、次の ping にだけ `today.md` の中身を載せる。
  - session の最初の ping。夜の切り替え（[ADR 0009](0009-long-term-memory-and-nightly-session-switch.md)）と昼寝の後の session も含む。
  - compaction（ADR 0009 の「上限での compaction」）の後の最初の ping。
- ほかの ping には載せない。なつみは、前に載った計画と、自分の書き込みを手がかりに進める。
  今の中身を確かめたいときは、`read` で読む。`read` で読んだものはターンを畳んでも残る（[ADR 0047](0047-folding-ended-turns-with-a-memo.md)）。
- ADR 0047 のターンの畳み込みでは載せ直さない。畳み込みは届いた出来事の行を残すので、載せた計画は消えない。
  消えるのは compaction の要約のときである。
- 載せたかどうかは、サーバーのメモリだけで覚える。SQLite には持たない。
  - サーバーが再起動して忘れたら、同じ session でも、次の ping にもう一度載せる。再起動は日常ではないので、二度載ることを受け入れる。
  - `today.md` が無いときは何も載せず、載せたことにもしない。
- 載せるのは、HEAD にコミットされた `today.md` である（`postbox/` と同じ。ADR 0076）。ターンの終わりの検査を通った長さに収まる。
- 計画は出来事の欄の 1 つとして載せる。欄の名前は実装の PR で決める。出来事はユーザーのメッセージの側にあるので、prefix は動かない。
- system prompt とツールの説明には、計画も目標も載せない。

### 長さ: 長く続く目標のファイルと `today.md` に、書くときの上限

- 長く続く目標のファイル 1 つと、`today.md` に、それぞれ長さの上限を掛ける。
- 上限は、ターンの終わりの検査で掛ける（ADR 0020 と同じ）。超えたファイルは直前のコミットの状態に戻し、理由を次のターンの入力に添える。
- 上限の値は設定で決める。既定の値は実装の PR で決める。1 ファイルの上限（`loop.memoryFileMaxChars`）より小さく取る。
- 片づけは、なつみが書くときに行う。
  - 済んだ短い目標は、毎朝の計画のときに消す。
  - 古い「今の様子」は、上限に当たったときになつみが要約する。
- 記憶の整理係（[ADR 0055](0055-a-memory-curator-at-night.md)・ADR 0068）は、`goals/` を変えることも動かすこともしない。
  目標の ID はファイル名なので、整理係が改名や移動をすると ID が変わる。同意の要る部分を、本人の同意なしに書き換えることにもなる。
  `postbox/` と `skills/` と同じ扱いである。

### 最初の goals: なつみが案を作り、本人に持ちかける

- 長く続く目標が 1 つも無いとき、なつみは `always.md`・性格・これまでの会話から、長く続く目標と日課の案を作り、本人に持ちかける。
  本人がうなずいたものを書く（同意の要る部分の流れのまま）。
- 持ちかけたことは `today.md` に書く。返事を待つ間の ping で、同じ案を何度も持ちかけない。
- すでに `always.md`・マニュアル・繰り返しの予約に目標を書いているインスタンスは、それを長く続く目標と日課に移すことも持ちかける。
  - 移した後に `always.md` に残る重複は、なつみが夜に消す。
  - 時刻が大事な繰り返しの予約は残す。
- これはインスタンスごとの導入の流れである。サーバーに移行の処理は足さない。

### SQLite には何も足さない

- 目標、計画、載せたかどうか、同意の要る部分の変更の一覧の、どれも SQLite に持たない。migration は無い。

### 進め方

1. この ADR。
2. natsumi: ping の説明の書き換え、ping に今日の計画を載せること、`goals/` の長さの上限と設定、`goals/` の下のサブディレクトリを戻す検査、
   整理係の対象から `goals/` を外すこと、ダッシュボードの一覧、マニュアル `manual/goals.md`、評価のシーン（計画のある ping と、計画が済んだ ping）。
3. 各インスタンス: 最初の goals を、なつみが本人に持ちかける（前の節）。記憶の中身なので、本人の同意の後に行う。

### 置き換える既存の決定

- ADR 0014
  - 置き換え: ping を「何かしたいことは？」の合図とし、何もなければそのまま終えること。今日の計画に沿って進める合図にする。
  - 追加: ping の出来事に、session の最初と compaction の後の最初にだけ、今日の計画の中身を載せる。
  - 残す: ping を出す時間帯と間隔、静かさの数え方、未確認の知らせの件数を添えること。
- ADR 0018
  - 追加: サーバーが名前を決めるものに、記憶の直下の `goals/` を加える。
- ADR 0020
  - 追加: ターンの終わりの検査で掛ける上限に、長く続く目標のファイルと `today.md` の上限を加える。
- ADR 0055・ADR 0068
  - 追加: 整理係の対象から、記憶の下の `goals/` を外す。
- ADR 0049
  - 追加: ダッシュボードに、goals の同意の要る部分の変更の一覧を足す。
- ADR 0063
  - 残す: 時刻が大事な定期の仕事は、繰り返しの予約のままである。日課は時刻を決めない。

## Consequences

- ping のターンに、何をするかの手がかりができる。計画の仕事がある間は、ping のターンでツールを呼び、モデルの呼び出しが増える。
  サブスクリプションなら利用量、自前のエンドポイントなら負荷として表れる。文脈も早く伸び、compaction が増える。
- 日付が変わって最初の ping は、目標を見渡して計画を立てるので、ほかの ping より重い。
- 計画が済み、今日できる短い目標も無い日の残りの ping は、今と同じく何もせずに終わる。
- ping に計画が載るのは 1 つの session で数回だけである。毎回載せる形より、履歴に積もるものが少ない。
  一方、その後に計画を書き換えたとき、なつみが新しい中身を知るのは、自分で書いた覚えか `read` だけである。
- ping の説明が変わるので、この版を入れた最初の session では prefix cache が効かない。その後は今までどおり固定である。
- 同意の要る部分を、なつみが同意なしに書き換えても、サーバーは止めない。気づけるのは、本人がダッシュボードの一覧を見たときである。
- 目標と計画は記憶の Markdown なので、本人は ssh で直せ、git の履歴で経緯を追える。サーバーの再起動で失うものは、載せたかどうかの覚えだけである。
- 長さの上限に当たると、その変更が丸ごと戻る。なつみは理由を読み、要約してから書き直す。
- 整理係が `goals/` を見ないので、目標のファイルの古いところを片づけるのは、なつみだけである。
- 日課は時刻を決めないので、日課を何時にやるかは保証されない。時刻が大事な仕事を日課に移すと、遅れたり、その日にできなかったりし得る。
