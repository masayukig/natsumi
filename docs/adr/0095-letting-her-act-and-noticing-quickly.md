# 0095. なつみは自由に動かし、守りは「防ぐ」より「すぐ気づく」に寄せる

- Date: 2026-11-09
- Status: Accepted

## Context

これまでのなつみの守りは、閉じ込めで防ぐことを軸にしてきた。

- Pi のツールは許可リストで絞り、任意 HTTP と任意 credential の読み出しを許さない（[ADR 0004](0004-pi-tool-and-voice-boundaries.md)）。
- 作業環境は閉じ込めたコンテナで、出口は許可リストで絞る。作業環境の外向きは、既定で全部拒否する（[ADR 0011](0011-memory-shell-in-a-confined-container.md)、[ADR 0019](0019-a-workspace-not-a-memory-tool.md)、[ADR 0034](0034-an-allow-list-for-the-way-out.md)）。
- クラスタの運用を受け持つインスタンス（ペネロペ）にも、鍵を見せない中継を API ごとに置き、行き先・パス・method を固定した（[ADR 0085](0085-relays-that-add-the-keys-for-the-workspace.md)）。

この形では、ペネロペの運用の作業が楽にならない。

- 中継は「通す」か「403 で断る」かの 2 つしか持たない。本人に聞く、許したことを台帳に残す、操作の意味で判定する、のどれも無い。
- ペネロペに新しい操作を 1 つ許すたびに、環境のリポジトリの PR、試験、反映、Pod の作り直しが要る。
  そのため、運用の作業で要る書き込み（workload の更新、Job の作成など）の多くを渡せていない。

本人は、なつみのコンセプトを「AI Agent でどれだけのことができるかを知りたい」に寄せたいと考えている。
本人は、閉じ込めて守らなければならないほどの秘密を持っていないとし、ある程度自由に動かした上で、
クラスタが乗っ取られたり攻撃されたりしていることにすぐ気づけることを求めた。
その代わりに監査を厚くし、異常にすぐ気づける体制を作る、というのが本人の方針である。

この方針の最初の適用として、ペネロペの出口に関所を置く。用語は次のとおりである。

- **関所**: なつみと同じ Pod の別のコンテナで動く、別のプログラム（リポジトリ `yuanying/natsumi-sentinel`）。
  作業環境などの外向きの通信を透過型の proxy で受け、宛先と操作ごとに、通す・本人に聞く（ask）・断るを決める。
  本人が許したことの台帳と、通したもの・断ったものの監査の記録を持つ。
  ADR 0040 のポッポさんの判定（Slack の投稿の前に掛ける関所）とは別のものである。この ADR とその後の ADR で単に「関所」と書くときは、こちらを指す。
- **authd**: 関所と同じ Pod の別のコンテナで、鍵を持つ。関所も作業環境も鍵を見ない。
- **サロゲート**: 道具やサーバーが鍵の代わりに持つ、秘密でない代わりの値。authd が、登録した宛先にだけ本物の鍵に差し替える。

関所と authd の中身（透過の仕方、操作の表、台帳、監査、鍵の差し替え）は、natsumi-sentinel の ADR が決める。

## Decision

### 方針: 自由に動かし、すぐ気づく

- なつみのインスタンスは、できるだけ自由に動けるようにする。守りは、閉じ込めて防ぐことより、**監査を厚くして異常にすぐ気づくこと**を主にする。
- 防ぐことで守る範囲（床）は、次の 2 つに絞る。
  1. **監視そのものを壊せないこと。** 監査の記録、関所と authd、異常の知らせの道、それらを置く場所と権限の仕組みを、なつみが書き換えたり止めたりできない。
     なつみが自分の守りを外せないよう、本人の答えを関所に渡す口（[ADR 0096](0096-sentinel-approvals-on-the-dashboard.md)）は、モデルのツールにも作業環境にも置かない。
     床と呼ぶ以上、次の道も塞ぐ。どれも、なつみの身元で直接は書けなくても、1〜2 手で監視を外せる道だからである。
     - **control plane。** API server などを動かす名前空間（kube-system など）を、なつみが書けない範囲に入れる。API server の引数を書き換えれば、監査のログも admission の規則も止められる。
     - **別の身元への乗り換え。** 強い権限の ServiceAccount がある名前空間を、なつみが書けない範囲に入れる。
       なつみが作る・直す Pod には、default 以外の ServiceAccount、hostPath、特権、host の名前空間を許さない。縛るのはこの乗り換えの道だけで、Pod の欄を 1 つずつ縛ることはしない。
     - **クラスタごとの乗っ取り。** 知らせが途絶えたことを知らせる仕組み（dead man's switch）の受け手を、クラスタの外に置く。クラスタの中の知らせの道は、クラスタごと取られると黙るからである。
  2. **本人の私事と、本人に代わる約束。** 次の 2 つは、これまでどおり気をつけ、今ある決定を変えない。
     - 本人の私事（記憶、会話、Gmail、Calendar など）を外へ流すこと。
     - 本人に代わって約束すること（Slack への投稿、Calendar の作成・変更など。[ADR 0003](0003-assistance-and-integrations.md)、[ADR 0012](0012-slack-and-colleagues.md)、[ADR 0040](0040-the-dove-sends-what-the-judge-passes.md)）。
- 床の外の行為は、許したうえで記録し、異常の知らせで気づく。床の外の行為で本人に聞く（ask）のは、本人がその場で判断したいものに限る。
- 防ぐことを緩めるときは、その行為を記録して異常に気づける手段を、同じ時に用意する。気づく手段の無いまま緩めない。
  - ペネロペの Kubernetes の権限（RBAC）を広げるのは、API server の監査のログと、クラスタの外の dead man's switch が動いてからとする。
    関所からは、クラスタの中で起きたこと（ペネロペが作った workload のふるまい）が見えないからである。
  - 関所を通る出口では、最初の版から、要求の中身を判定する仕組み（判定器）なしでできる「いつもと違う」の知らせ（初めて見る宛先や操作と対象の組を 1 件ずつ知らせること、1 日 1 回のまとめ）を持つ。中身は natsumi-sentinel の ADR-0006 が決める。

### 守る対象・許す範囲・失敗したときの倒し方

- 守る対象: 監視そのもの（監査の記録、関所と authd、知らせの道）と、本人の私事と本人に代わる約束。
- 許す範囲: 床の外の行為は、記録して気づける手段があるものに限って許す。
- 失敗したとき: 記録や知らせの手段が無いか止まっているときは、緩めない側に倒す。関所が止まれば、関所を通る出口は止まる（natsumi-sentinel の ADR）。
  知らせそのものが途絶えたときは、クラスタの外の dead man's switch が本人に知らせる。

### 閉じ込めの ADR は、触れるたびに見直してよい

- ADR 0004・0011・0019・0034・0085 などの閉じ込めの決定は、この ADR だけでは変えない。どれも Accepted のまま残る。
- 後の ADR がこれらの決定に触れるときは、この方針で見直してよい。見直すときは、次の問いで残すか緩めるかを決め、その ADR の「置き換える既存の決定」に書く。
  - その閉じ込めは、床（監視を壊せないこと、本人の私事と約束）を守っているか。守っていれば残す。
  - 床を守っていないなら、記録と知らせで気づける形に置き換えられるか。置き換えられるなら緩めてよい。
- 閉じ込めの ADR の Context や理由に「防がなければならない」とある箇所は、この方針より前の判断である。読むときはこの ADR と合わせて読む。

### 適用の範囲: 関所を選んだインスタンスから

- この方針を最初に適用するのは、ペネロペである。関所に関わる natsumi の機能は、どれも config に書いたときだけ有効で、既定は off とする。
  natsumi の image はインスタンスに共通のまま、選ばないインスタンスは今の閉じ込めのままである。
- 関所を選んだインスタンスでは、既存の決定を次のように読み替える（下の「置き換える既存の決定」）。
  - 作業環境の外向きは、宛先を問わず関所が受ける。作業環境の道具は本物の URL に話し、鍵の代わりにサロゲートを持つ。
    通すか、聞くか、断るかは関所が宛先と操作ごとに決める。
  - サーバーの出口は、最初の版では関所を通さない。外のエージェントへの依頼（`ask_agent`）を関所に通す形は、判定器を入れる関所の版で決める（[ADR 0097](0097-asking-agents-through-the-sentinel-with-a-surrogate.md)、Proposed）。
  - 関所が本人に聞くものの答えは、本人がダッシュボードで出す（ADR 0096）。
- ほかのインスタンス（本人の秘書など）へ広げるのは、ペネロペで形が固まった後とし、そのときの ADR で決める。

### 本 ADR で決定しないこと

- 関所の通り道、宛先ごとの扱い、操作の表、台帳と監査の記録、鍵の差し替えの仕組み、関所の「いつもと違う」の知らせの中身（委譲先: natsumi-sentinel の ADR（リポジトリ `yuanying/natsumi-sentinel` の `docs/adr/`））。
  関所の ADR は、この ADR の方針を決め直さず、それを受けて関所が何をするかを書く。
- クラスタの側の床の中身（ペネロペの ServiceAccount の RBAC、書けない名前空間の一覧、Pod の縛り方と admission の規則、GitHub の側の権限）、API server の監査のログ、クラスタの外の dead man's switch、異常の規則と知らせの届け先（委譲先: 環境のリポジトリの運用手順と設定）。
- ペネロペの VM の出口と、ペネロペの private のリポジトリで動く GitHub Actions の出口。どちらも関所を通らない（委譲先: それを手当てするときの ADR）。
- 本人の秘書のインスタンスなど、ペネロペ以外への適用（委譲先: 広げるときの ADR）。
- 閉じ込めの ADR の 1 つずつの見直し（委譲先: その ADR に触れる後の ADR）。

### 置き換える既存の決定

どれも、関所を選んだインスタンスに限る。選ばないインスタンスでは変わらない。

- ADR 0004
  - 置き換え: Decision の「任意 HTTP を許可しない」。作業環境は、関所の表にある宛先へ本物の URL で HTTP を使える。通すかどうかは関所が操作ごとに決める（ADR 0085 の Decision「HTTP の API は、loopback の中継が認証を付けて HTTPS で送る」の、中継が固定した行き先・パス・method に限る点も、関所の表に置き換わる）。
  - 残す:「任意 credential 読み出しを許可しない」。鍵は作業環境にもサーバーにも置かない。サロゲートは鍵ではない。
- ADR 0034
  - 置き換え: Decision「作業環境の外向きは、今は全部拒否する」（ADR 0085 で決め直した形を含む）。作業環境の UID の外向き（名前解決を含む）は、すべて関所へ回す。関所の名前解決は、表にある名前にだけ答える。
  - 残す: 規則は初期化のコンテナだけが張り、常駐するコンテナは `NET_ADMIN` を持たないこと。UID で誰の通信かを見分けること。サーバーの外向きは、外のエージェントへの HTTPS を含めて、今の透過型の proxy を名前で通すこと（変えるかは ADR 0097 で決める）。
- ADR 0085
  - 置き換え: Decision「HTTP の API は、loopback の中継が認証を付けて HTTPS で送る」の作業環境の loopback の中継と、Decision「道具は、宣言したツールと run_shell から使う」の中継を指す設定（kubeconfig の中継の URL など）。関所と authd がこの役を受け持つ。
  - 置き換え: Decision「作業環境の SNI の許可リストは作らない」。作業環境の HTTPS は、関所が受けて宛先と操作で判定する。
    この節の理由（作業環境が要求の認証を自由に書けば、他人の token で書き込めてしまう）に応えるのは、関所の判定と authd の差し替えである（natsumi-sentinel の ADR）。
  - 残す: 作業環境とモデルは鍵を 1 つも見ないこと。ssh を ssh-agent のコンテナで扱うこと（ssh はサロゲートにできない）。`run_shell` の説明を変えないこと。

## Consequences

- ペネロペに渡せる操作が増える。許すたびに環境のリポジトリを直して Pod を作り直す代わりに、関所が本人に聞き、本人の許しを台帳に残して通す。
- 本人は「AI Agent でどこまでできるか」を、閉じ込めに妨げられずに試せる。
- 防がないものは、起きてから気づく。気づくまでの間に起きたこと（クラスタの中の書き換え、読まれたもの）は戻らない。これを受け入れる。
- 守りの強さは、監査と知らせが正しく動いていることに依る。監視が黙って止まれば、何も守らない。監視が止まったこと自体を知らせる仕組みが欠かせなくなり、その受け手をクラスタの外に用意しなければならない。
- 床を塞ぐために、ペネロペは control plane と強い ServiceAccount のある名前空間に書けず、別の ServiceAccount・hostPath・特権・host の名前空間を使う Pod を作れない。そうした作業は本人の手に残る。
- RBAC を広げられるのは、API server の監査のログとクラスタの外の dead man's switch が動いてからである。それまでは、ペネロペの Kubernetes の書き込みは増やせない。
- 閉じ込めの ADR の理由には、この方針より前の「防がなければならない」が残る。後から読む人は、この ADR と合わせて読まなければ、今の守りの考え方を取り違える。
- 本人の私事と約束の扱いは変わらないので、本人の秘書の使い勝手と守りは、この ADR では変わらない。
- 関所を選んだインスタンスと選ばないインスタンスで、作業環境の出口の形が 2 通りになる。マニュアルと手引きも 2 通り要る。

## Alternatives Considered

- **閉じ込めを保ち、許す範囲を中継ごとに少しずつ広げる**: 許すたびに PR と Pod の作り直しが要るという困りごとが残る。本人に聞く・台帳に残すという道も無いままである。
- **閉じ込めの ADR を、この ADR でまとめて置き換える**: どこを残しどこを緩めるかは、それぞれの決定に触れるときでないと判断できない。まとめて置き換えると、床を守っていた決定まで根拠を失う。
- **床を「うっかりと浅い乗っ取りまで防ぐ」と言い直し、深い乗っ取りはクラスタの外の見張りだけで気づく**: control plane と別の身元への乗り換えを塞がずに済む。一方で、監視を外されたあとに起きたことは記録に残らず、外の見張りが知らせるのは途絶えたことだけである。床と呼ぶものは言葉どおり塞ぐことにし、外の見張りはそれに重ねる。
- **方針を関所の承認の窓口の ADR の Context にだけ書く**: 方針は窓口より広く、閉じ込めの ADR を見直すときの基準になる。後の ADR から番号で指せるよう、独立の ADR にした。
