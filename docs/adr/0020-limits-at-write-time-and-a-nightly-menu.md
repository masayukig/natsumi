# 0020. 上限は書くときに掛け、夜は手順ではなく候補にする

- Date: 2026-09-20
- Status: Accepted（夜の候補から重複・古いところの手直しとトピックの統合・分割・改名・フォルダの整理を外し、記憶の整理係の仕事にすることは [ADR 0055](0055-a-memory-curator-at-night.md) で置き換え）

## Context

[ADR 0018](0018-memory-in-git-and-the-nightly-rebuild.md) で記憶を git のリポジトリにし、
[ADR 0019](0019-a-workspace-not-a-memory-tool.md) でその周りをなつみの作業環境にした。
実装に入る前に、この 2 つが残していた細部を詰めた。
常時記憶が上限を超えたときの扱い、引き継ぎをファイルへ移した後に SQLite へ残る列、
再起動のときに system prompt をどう組み直すか、そして夜の再構成の指示である。

詰めていく中で、次のことが分かった。

- **上限の超過は、そもそも起こさずに済む。** ADR 0018 は「常時記憶が上限を超えていたら prompt に入れず、
  代わりに警告を書く」と決めていた。その警告の文面と、警告を読んだなつみが削るまでの間の振る舞いを詰めていたところで、
  「そもそも超えないようにできないのか」という問いが出た。
  記憶リポジトリの検査には、既に **「長すぎるファイルを直前のコミットへ戻し、理由を返す」** 仕組みがある（ADR 0018）。
  常時記憶用の上限をそこに足せば、超過という状態そのものが作られなくなる。
- **引き継ぎが二重になっていた。** ADR 0018 は引き継ぎを `handoff.md` へ移したが、
  SQLite の切り替えの記録にある引き継ぎの列（ADR 0009）をどうするかは書いていなかった。
  同じものが 2 か所にあり、どちらが正かが決まっていない。
- **列を消して不変条件を表の CHECK に移そうとすると、migration が失敗する。**
  切り替えの記録には、引き継ぎがまだファイルに無かった頃の完了済みの行が既にある。
  SQLite の表 CHECK は既存の行にも掛かるので、「切り替え済みなら引き継ぎのコミットがあること」を CHECK で書くと、
  その古い行で引っかかる。古い行を偽の値で埋めるのは履歴に嘘を書くことになる。
- **夜にやらせたい項目が 3 つから 10 個近くに増えた。** ADR 0018 の時点では、記憶の組み直し・常時記憶・性格の見直しが中心だった。
  そこに ADR 0019 が「作業場の棚卸し」と永続領域の片づけを足した。
  一方で、運用中のある夜の振り返りは、記憶の整理だけでモデル呼び出しの上限に張り付き、
  引き継ぎを書いたのは終わり際だった。**あと数回遅ければ、その夜の切り替えは失敗していた**（ADR 0009）。
  手順として端から並べると、後ろの段ほど実行されない。そして最後尾にあるのが、一番落としてはいけないものだった。
- **性格の自己編集は、追加の作業が要らない。** ADR 0018 は `personality.md` をなつみ自身が夜に書き換えてよいと決めた。
  実装を読み直すと、夜だけ書ける対象に `personality.md` が入っており、性格は session を作るときに記憶リポジトリから直接読まれていた。
  つまり既に書き換えられる。**「未実装」と記録にあっても、実装を見るまでそう扱わない。**

もう 1 つ、背景として掛かっている制約がある。バックエンドは prefill が遅いので、prompt は可能な限り prefix cache に乗せたい。
再開のときに system prompt をバイト単位で再現するには、引き継ぎと性格と常時記憶をコミットで固定し、そこから組み直すことになる。
これを詰めている途中で、**オーナーが「prefix cache を壊さないのは可能な限りという意味であって、常に避けるべき要件ではない」と明言した。**
制約の強さを取り違えたまま設計すると、日常ではない出来事のために常時の複雑さを買うことになる。

## Decision

### 常時記憶の上限は、書くときに掛ける。読むときは素通しにする

- 常時記憶の上限（`loop.alwaysMemoryMaxChars`）は、**コミットのときの検査で掛ける。**
  ターンの終わりの検査で `always.md` が上限を超えていたら、他の検査と同じく直前のコミットの状態へ戻し、理由を次のターンの入力に添える。
  夜の再構成で戻した場合の伝え方も、他の検査と同じである（ADR 0018）。
- **prompt を組む側は、長さを見ない。** `always.md` の中身をそのまま system prompt に入れる。
- ADR 0018 の「上限を超えていたら中身を入れず、代わりに警告を書く」をやめる。
  超過した常時記憶は、そもそもコミットされない。
- **例外として、オーナーが手で直した結果が上限を超えていれば、そのまま prompt に入る。** これを受け入れる。
  - サーバーがコミットしたものは必ず上限の中にある。残るのは、オーナーが自分の git で直接コミットした場合だけである。
  - その場合に prompt から常時記憶が丸ごと消えるのは、直した本人にとって分かりにくい振る舞いである。
    書いたものがそのまま入るほうが、原因と結果が近い。
  - 上限は compaction の上限に対して十分小さく取ってあり（ADR 0018）、多少超えても壊れるものではない。
- **「起きたら対処する」を設計する前に、「起こさない」ができないかを問う。**
  警告の文面、警告を読ませる経路、削られるまでの間の振る舞いが、まるごと要らなくなった。

### 引き継ぎは `handoff.md` を正とし、SQLite からは列を消す

- 引き継ぎの本文は `handoff.md` にだけ置く。**新しい session の system prompt に入れる引き継ぎも、このファイルから読む。**
  SQLite を経由しない。
- 切り替えの記録から、引き継ぎの本文を持つ列を消す（schema 8）。
  代わりに、**その切り替えで prompt に入った `handoff.md` のコミットを記録する。**
  - 記録として残したいのは本文ではなく、**どの session がどの引き継ぎで始まったか**である（ADR 0018）。
    本文は git の履歴にあるので、コミットを指せば辿れる。
  - 本文を 2 か所に持つと、片方だけが直されたときに、どちらが prompt に入ったのか分からなくなる。
- 既存の完了済みの行では、このコミットは NULL になる。
  **NULL は「その切り替えの時点では引き継ぎがファイルに無かった」を正しく表すので、嘘にならない。**
  値を捏造して埋めることはしない。

### 不変条件は、表の CHECK ではなくコードで守る

- 「切り替えが完了しているなら、引き継ぎのコミットが記録されている」という不変条件に、**表の CHECK を付けない。**
- SQLite の表 CHECK は新しい行だけに掛けられない。既存の行に遡って掛かるので、
  上記の NULL を持つ古い行で migration が落ちる。
- **不変条件はコードの側で守る。** 新しく書く切り替えの記録が条件を満たすことは、テストで確かめる。
- 一般化すると、**移行の前と後で意味が変わる列に、宣言的な制約を後から足さない。**
  制約が表せるのは「いま正しいこと」だけで、「これから正しくすること」は表せない。

### 再開のときの system prompt は、作業ツリーの今の中身から組む

- サーバーの再起動で今の session を使い続けるとき、system prompt は **`personality.md`・`always.md`・`handoff.md` の、
  そのときの作業ツリーの中身**から組む。記録してあるコミットから復元しない。
- ADR 0009 は、引き継ぎを SQLite に置く理由の 1 つに **「再起動のときは、記録から同じ system prompt を作り直せる」** を挙げていた。
  この点は成り立たなくなる。ファイルが変わっていれば、再起動後の prompt も変わる。
- **prefix cache を失うことを承知で、単純なほうを採る。**
  - 再起動は日常ではない。日常で prefix を壊さないこと（走っている session の instructions を差し替えない、
    ツールの説明を動的に組み立てない）は変えない。
  - コミットから復元する形は、コミットの記録・取り出し・作業ツリーとの食い違いの扱いを、常時抱えることになる。
    日常ではない出来事のために払う代償として重い。
  - 記録してあるコミットは、後から「どの引き継ぎで始まったか」を辿るために使う。prompt を組み直すためではない。
- **制約の強さを取り違えると、設計が不必要に複雑になる。**
  「可能な限り」と「絶対に」は違う要件であり、どちらなのかを設計の前に確かめる。

### 夜の再構成は、手順ではなく候補として渡す

- ADR 0018 の 8 段の手順をやめる。夜のターンには、**やれることの一覧を候補として渡し、
  その夜に何をやるかはなつみが選ぶ。**
- **必須は 2 つだけとする。**
  - 明日の自分への引き継ぎを書くこと。
  - ターンを終えること（本人には何も送らない）。
- 候補には、少なくとも次を含める。
  - 記憶全体を読み直し、今日のことのうち残すものを書く。
  - 重複と、古くなったものを直す。
  - トピックの統合・分割・改名と、フォルダの整理。
  - 常時記憶の見直し。
  - 性格の見直し。
  - 今夜の変更の説明を書くこと。
  - **残っているプロセスの棚卸し**（ADR 0019）。
  - **検査もコミットもされない永続領域の片づけ**（ADR 0019）。
- **やらなかったことは、引き継ぎに書かせる。** 翌夜の自分がそれを読んで拾う。
  夜の指示には、この一文を必ず入れる。
- 順序を固定しない理由。
  - 項目が 10 個近くあり、上限のあるターンでは全部は終わらない。手順として並べると、後ろの段ほど実行されない。
  - **必ず落としてはいけないものが最後尾に来る形は、失敗の仕方が悪い。**
    引き継ぎが書かれないと、その夜の切り替えそのものが失敗する（ADR 0009）。
    実際に、記憶の整理だけで上限に張り付き、引き継ぎがぎりぎりだった夜がある。
  - その夜にやる価値があることは、その夜の状態で変わる。記憶が荒れている夜もあれば、作業場が散らかっている夜もある。
    どれを優先するかは、記憶と作業場を実際に見たなつみのほうがよく分かる。
- 回数の上限は `loop.reviewModelCalls` の設定で決まる。ADR 0018 は既定として 40 を書いたが、
  項目が増えた分、運用ではこれより大きな値にしてある。**ADR としてこの値を固定しない。**
  設定キーとして出してあるので、値を変えるのに変更も再構築も要らない。

### 引き継ぎを書ける時間と、変更の説明を書ける時間

- `handoff.md` は、**いつでも書ける。** 夜だけ書けるのは `always.md` と `personality.md` の 2 つに限る（ADR 0018 のまま）。
  日中に書く理由は普通は無いが、禁じる理由も無い。この 2 つと違って、日中の会話の途中で中身が prompt に入り直すことはない。
- そのため、**引き継ぎを prompt に入れるときの文面は、「昨夜書いた」と断定しない。**
  いつ書かれたかを prompt が名乗ると、日中に書き直された場合に実態とずれる。
  引き継ぎは「前の自分が次の自分へ残したメモ」であって、書かれた時刻はその意味に要らない。
- 今夜の変更の説明を書くツール（`write_change_note`）は、**夜の再構成のターン以外で呼ばれたら、理由を返して拒否する。**
  これはその夜のコミットメッセージになるもので、日中のコミットはサーバーが機械的に付ける（ADR 0018）。
  夜だけ書ける記憶のファイルと同じく、**黙って無視せずに理由を返す。** 理由が返れば、なつみは何が起きたのかを知って書き直せる。

### 性格の自己編集

- ADR 0018 の決定（なつみ自身が夜に `personality.md` を書き換えてよい）を、そのまま残す。**追加の作業は無い。**
  夜だけ書ける対象に入っており、性格は session を作るときに記憶リポジトリから読まれている。
- **記録に「未実装」とあっても、実装を読むまでそう扱わない。**

### 持ち越さないこと

- 常時記憶が上限を超えたときの警告の文面。超過はコミットされないので、警告そのものが要らなくなった。
- 引き継ぎのコミットから system prompt を復元する仕組み。作業ツリーから組むので要らない。

## 置き換える既存の決定

- **ADR 0018**
  - 置き換え:「常時記憶」の節のうち、**「上限を超えていたら、中身を入れない。代わりに『常時記憶が上限を超えているので
    読み込んでいない。夜に削ること』を prompt に書く」**。上限はコミットのときの検査で掛け、読む側は素通しにする。
  - 置き換え: 設定の表の `alwaysMemoryMaxChars` の意味。「超えたら prompt に入れず、警告を書く」から
    「超えたファイルは直前のコミットに戻す」へ。`memoryFileMaxChars` と同じ性質の上限になる。
  - 置き換え:「夜の再構成」の節の **8 段の手順**。候補の一覧と、必須 2 つに変える。
  - 置き換え: 同じ節の「このターンのモデル呼び出しの上限を 16 回から 40 回へ」のうち、**40 という値**。
    値は設定で決める。時間の上限（30 分）は変えない。
  - 追加:「記憶のリポジトリ」の節の「どの session がどの引き継ぎで始まったかは、これまでどおり SQLite の切り替えの記録に残す」を、
    **本文ではなく `handoff.md` のコミットを記録する**形に具体化する。
  - 追加: 変更の説明を書くツールを、夜のターン以外で呼ばれたら拒否すること。
  - 残す: 記憶のリポジトリと固定の 3 つのファイル、記憶の読み書きを shell に一本化すること、
    ターンの終わりのコミットとそのときの検査、`always.md`・`personality.md` を夜だけ書けること、性格の扱い、移行、
    git の CLI をサーバーが実行すること。
- **ADR 0009**
  - 置き換え: 引き継ぎを新しい session の system prompt に入れる理由のうち、
    **「再起動のときは、SQLite の記録から同じ system prompt を作り直せる」**。
    引き継ぎは SQLite に保存されなくなり、再開のときの prompt は作業ツリーの今の中身から組む。
  - 置き換え: 手順 3 の「引き継ぎは書かれた時点で SQLite に保存する」。保存先は `handoff.md` である（ADR 0018）。
    書かれたときに本人に届く出力と同じ検査を掛けることは変えない。
  - 残す: 夜に session を切り替えること、その手順・失敗の扱い・切り替え中の振る舞い、
    引き継ぎを新しい session の system prompt に入れること（最初の入力にはしないこと、日中の compaction で変わらないこと）。

## Consequences

- 常時記憶が上限を超えた状態は、サーバーが作らなくなる。超過の警告と、それを読んで削るまでの間の振る舞いが要らない。
  代わりに、**夜に常時記憶を書き直して上限に当たると、その変更が丸ごと戻る。**
  理由は次のターンの入力（夜なら新しい session の prompt）に届くが、夜に戻った場合、書き直せるのは次の夜になる。
  これは他の記憶のファイルと同じ性質である（ADR 0018）。
- オーナーが手で上限を超える常時記憶をコミットすると、そのまま prompt に入る。
  入力が想定より増えるが、compaction の上限に対しては小さいままである。
- 引き継ぎが 1 か所になる。オーナーは git の履歴で引き継ぎの変化を追え、
  切り替えの記録からは、どの session がどのコミットの引き継ぎで始まったかを辿れる。
- 引き継ぎの本文を SQLite から読む経路が無くなるので、**記憶リポジトリが読めない状態では、切り替えも再開もできない。**
  記憶が作業環境のコンテナ越しにしか書けないこと（ADR 0018）に続いて、依存がもう 1 つ増える。
- 古い切り替えの行は、引き継ぎのコミットが NULL のまま残る。
  この列を読むものは NULL を扱えなければならない。不変条件が表に書かれていないので、
  **新しい行が条件を満たすことは、コードとテストだけが保証する。**
- 再起動のたびに、system prompt はそのときのファイルの中身になる。
  ファイルが変わっていれば prefix cache は失われ、その session の続きは prefill からやり直しになる。
  再起動は日常ではないので、これを受け入れる。
  一方で、**再起動を挟むと「同じ session なのに system prompt が違う」状態が起こり得る。**
  session の記録を後から読むとき、そこにある prompt が今の prompt と同じとは限らない。
- 夜に何が行われるかが、その夜ごとに変わる。**サーバーは、記憶が組み直されたことも、棚卸しが行われたことも保証しない。**
  保証するのは引き継ぎが書かれたことだけである。何が行われたかは git の履歴と引き継ぎに残る。
- 候補から選ばせる形は、選ぶこと自体にモデルの判断を使う。手順どおりに進めるより、始めの数回の呼び出しが選択に使われる。
  その代わり、上限で打ち切られたときに落ちるのは、**なつみがその夜に重要でないと判断したもの**になる。
- 「やらなかったことを引き継ぎに書く」は、引き継ぎの役割を 1 つ増やす。
  引き継ぎは明日の自分への申し送りであると同時に、夜の作業のやり残しの記録にもなる。長さは増える。
