# 0071. ブラウザのチャットからファイルを上げ、本人のメッセージに添える

- Date: 2026-10-06
- Status: Accepted

## Context

本人は、ブラウザのチャット（[ADR 0058](0058-settings-and-chat-in-the-browser.md)）から、なつみにファイルを渡したいと考えた。
細部は本人との問答（Q1〜Q9）で決めた。この ADR の後に 2 つ（Q10・Q11）を決め、実装の PR で残りを決めて書き足した。

手元の事情は次のとおりである。

- ブラウザのチャットには、ファイルを添える手段が無い。`conversation.send` が運ぶのは文面（32 KiB まで）だけである。
  本人が資料を見せたいときは、中身を貼るか、別の道で置くしかない。
- Mac・iPhone のアプリも同じことを求められている。今回はブラウザだけを作り、アプリは後で同じ API を使う。
- 外から届くものは、可能な限り `sources_updated`（[ADR 0050](0050-telling-of-source-updates-with-one-event.md)）に寄せる方針である（[ADR 0069](0069-agent-replies-as-files-in-sources.md)）。
  中身はサーバーが `/sources` の下にファイルとして置き、出来事には場所と印（`attention`）と短い要約だけを載せる。
  `/sources` はサーバーだけが書き、作業環境からは読み取り専用である。`/sources` の下は 1 つの git の作業ツリーで、差分の見張りもこれで行う。
- `attention` に付いた画像は、出来事と一緒にモデルに画像として見せている。1 つの出来事で 4 枚までである。
  画像かどうかは拡張子ではなく中身で PNG・JPEG・WebP と見分ける（[ADR 0044](0044-drawing-with-sdctl-and-posting-images.md)・[ADR 0045](0045-showing-the-owner-images-with-a-reply.md)・[ADR 0048](0048-bringing-in-images-an-agent-hands-back.md)）。
- 本人のメッセージは、単一の思考ループに出来事（`mac_message`）として入る（[ADR 0008](0008-single-thinking-loop-and-mac-conversation.md)）。
  モデルには、ツールの引数に写させる ID を見せない（[ADR 0024](0024-no-event-ids-for-the-model.md)）。
- ブラウザの認証は cookie（`natsumi_session`、`SameSite=Strict`）である。状態を変える口は、Origin を照合する WebSocket とログアウトの POST だけに絞っている（ADR 0058）。

## Decision

### 受け付ける種類は絞らない

- ファイルの種類は何でも受け付ける。拡張子でも中身でも断らない。
- 読み方は、なつみが作業環境で決める（PDF なら `pdftotext` など）。
- 退けた案: 画像や PDF などに絞る。なつみが読める形は作業環境の道具で増えていくので、受け口で先に決めることになる。

### 届け方: `sources_updated` で知らせず、本人のメッセージに添える

- 添えたファイルは、本人のメッセージの一部として届ける。メッセージに置き場所を添え、本文と添付を 1 つの出来事にする。
- ファイルの置き場所だけは、方針どおり `/sources` の下にする（下の「置き場所」）。知らせを `sources_updated` にしないのは、本人のチャットのメッセージだけの例外である。
- 退けた案: 添付を `/sources` に置き、`sources_updated` の `attention` で知らせる。本人も一時はこれでよいと考えた。採らなかった理由は次のとおりである。
  - 本文と添付が 2 つの出来事に分かれると、なつみが処理する順序が保証されない。「この資料を見て」の本文が、資料より先に届くことがある。
  - 本文ごと `attention` にすると、本文と添付は 1 つになる。しかし、ブラウザへ返事を返す道（今は本人のメッセージへの `reply_to_mac`）と、画像は 1 イベント 4 枚までという上限を、`attention` の側で別に決め直す必要が出る。
  - 本人のチャットは、外から届く読みものではなく、会話そのものである。会話の 1 回の発言を割らない。

### 上限: 1 ファイル 25MB、一度に 10 個まで

- 1 つのファイルは 25MB まで、1 つのメッセージに添えられるのは 10 個までとする。
- どちらもサーバーの設定で変えられる。設定の名前は実装の PR で決める。

### 画像はそのまま見せ、ほかのファイルは置き場所だけを添える

- 中身で PNG・JPEG・WebP と見分けられたファイルは、メッセージに画像として載せ、置き場所も添える。`attention` の画像と同じ扱いである。
- ほかのファイルは、置き場所だけを添える。なつみは必要なら作業環境で読む。
- 退けた案: 画像も置き場所だけを添える。問答では最初これを推したが、既存の作りを確かめると、`attention` の画像はそのまま見せていた。先例に揃える。
- 画像として見せるのは、1 つのメッセージで 4 枚までとする（Q10）。`attention` の 1 イベント 4 枚と同じである。
  5 枚目からは画像として見せず、置き場所だけを添える。

### 置き場所: `/sources/uploads`

- 上げたファイルは、サーバーが `/sources/uploads` の下に置く。なつみからは読み取り専用で、本人が渡した原本がそのまま残る。
- `/sources/uploads` は、`/sources` の差分の見張り（git）から外す。理由は次の 2 つである。
  - メッセージで知らせたファイルを、`sources_updated` でもう一度知らせないため。
  - 大きいバイナリで、`/sources` の履歴が膨らまないようにするため。
- 退けた案: 作業環境の `/work/uploads` に置く。なつみが書き換えたり消したりでき、渡したときの原本が残らない。

### 保持: 消さない

- 送ったファイルは、当面は自動では消さない。量が問題になったら、そのときに方針を決める。

### 運び方: HTTP で先に上げ、送るときは ID を並べる

- ブラウザは、ファイルを選んだ時点で HTTP の POST でサーバーに上げる。認証はチャットと同じ cookie である。サーバーは上げたファイルの ID を返す。
- 送るときは、`/v1/ws` の `conversation.send` に、文面と一緒に上げたファイルの ID を並べる。
- この ID はブラウザとサーバーの間のもので、モデルには見せない（ADR 0024）。メッセージでなつみに見せるのは置き場所である。
- 上げたが送られなかったファイル（選んだ後に消した、ページを閉じた）は、サーバーが片付ける。
- POST は cookie で状態を変える口なので、ログアウトの POST と同じく Origin を `publicOrigin` と照合する（ADR 0058 の方針どおり）。
- 上げる口は、cookie に加えて Mac・iPhone の bearer でも受ける（Q11）。アプリの側の作業は後で行う。
- 退けた案: `/v1/ws` のメッセージに base64 で載せる。25MB を 10 個載せると 1 つの WebSocket の通信が数百 MB になり、送り終わるまで同じ接続のほかのやり取りが詰まる。base64 で 3 割ほど膨らむ。

### 画面: クリップのボタン、ドラッグ＆ドロップ、貼り付け

- ファイルは、入力欄の横のクリップのボタン、チャットへのドラッグ＆ドロップ、貼り付けの 3 つの道で添えられる。
- 送る前は、添えたファイルをファイル名のチップで並べ、画像は縮小して見せる。チップには削除のボタンを付ける。
- 会話の履歴の本人の発言にも、添えたファイルを出す。

### 実装で決めたこと

問答では決めず、実装の PR で決めたものは次のとおりである。

- **置き場所の名前**: `/sources/uploads/<UTC の日時 YYYYMMDDTHHMMSSZ>-<16 進 4 桁>/<名前>`。1 ファイルに 1 つのディレクトリなので、同じ名前のファイルがぶつからない。
  名前は、パスの区切り（`/`・`\`）の前を捨て、NFC に揃え（Mac は分解した形で送る）、制御文字を `_` に、先頭の `.` を `_` に替え、拡張子を残して 200 バイトまでに縮める。空や `.`・`..` は `file` にする。
- **書き方**: 届く間はサーバーだけの `.natsumi/uploads/` に書き、書き終えてから置き場所に移す。作業環境に書きかけは見えない。上限を超えた時点で書くのをやめ、何も残さない。
- **権限**: ディレクトリは 0750、ファイルは 0640。作業環境のグループは読めるだけである（[権限と秘密の一覧](../permissions.md)の「作業環境」）。
- **git の見張りから外す方法**: `uploads` を読みものとして登録しない（見張るのは登録した読みものの下だけ）うえで、`sources.git` の `info/exclude` に `/uploads/` を書く。`git status` にも出ない。
- **片付け**: どのメッセージにも付かないまま 1 日経ったファイルは、サーバーが行ごと消す。1 時間ごとと起動のときに見る。送ったファイルは消さない。
- **上げる口**: `POST /v1/uploads?name=<名前>` で、本文がファイルそのもの。返すのは `uploadId`・`name`・`bytes`（画像なら `mimeType`・`width`・`height`）。上限を超えれば 413。
- **取り戻す口**: `GET /v1/uploads/<uploadId>`。会話の画像と同じく、bearer か、cookie（GET は Origin を見ない）。メッセージに付いたものだけを返す。
  画像はその種類で、ほかは `application/octet-stream` と `Content-Disposition: attachment` で返し、どちらにも `Content-Security-Policy: sandbox` を付ける。
  これがブラウザが履歴の添付の中身を取る道である。縮小した画像は作らず、チップの縮小はブラウザが手元のファイルから作る。
- **送るときの検査**: `conversation.send` の `uploadIds`。同じアカウントが上げ、まだ送っていないものだけを付けられる（`upload-not-found`）。数は上限まで（`too-many-uploads`）。
  検査とメッセージへの記録は待ちを挟まずに行い、記録とファイルの割り当ては 1 つのトランザクションにする。ファイルだけのメッセージ（本文が空）も受ける。
  同じ requestId の送り直しは、本文とファイルが同じときだけ最初の結果で答える。
- **会話の記録**: ファイルはそれぞれ `uploads` の表の行で、付いたメッセージとその中の順を持つ。端末には、本人のメッセージの `attachments`（`uploadId`・`name`・`bytes`、画像なら種類と大きさ）で見せる。
  上限は `session.snapshot` の `uploads` で知らせる。
- **メッセージの中での書き方**: `mac_message` の `attachments` に、`{ "path": "/sources/uploads/…/名前", "bytes": 大きさ }` を送った順に並べ、画像として一緒に見せたものには `"shown_as_image": true` を付ける。ID は載せない。
- **見せる画像の大きさ**: 1 枚 5MB を超える画像は、画像として見せず置き場所だけにする。Slack の画像の既定の上限（`slack.maxImageBytes`）と同じで、モデルの受け口の大きさに収めるためである。
- **画像のあるメッセージと steer**: Pi の steer は本文だけを運ぶ作りにしているので、画像として見せるもののあるメッセージは、走っているターンに差し込まず、次のターンで画像と一緒に渡す。画像の無い添付は今までどおり差し込む。
- **設定の名前**: `uploads.maxFileBytes`（既定 26214400、1024〜512MiB）と `uploads.maxFiles`（既定 10、1〜50）。
- **本番の Ingress**: 前に立つ gated（v0.2.0）は本文の大きさに上限を持たない。本文を読む 1 回ごとに 60 秒の待ちの上限があるだけなので、25MB は通る。環境の設定を変える作業は足さない。
- **PR #134（Slack の PDF）との揃え**: 置き場所は揃えない。Slack の添付はチャンネルの記録の一部として `sources/slack/…/files/` に置き、こちらは本人が渡した原本なので `sources/uploads` に置く。
  PDF を読む道具（`poppler-utils`）は PR #134 が作業環境に入れる。こちらはなつみへの説明で道具を名指しせず、「作業環境で読む」とだけ書く。上限は、こちらが本人の渡すファイルのための設定で、Slack の PDF の固定の上限（20MiB）とは別にする。

### ADR との関係

- ADR 0058
  - 追加: ブラウザのチャットで、本人のメッセージにファイルを添えられる。上げる口は cookie で受け、Origin を照合する。アプリの bearer でも受ける。
  - 保つ: 状態を変える口は Origin を照合するものだけである。
- ADR 0050
  - 追加: `/sources/uploads` は `/sources` の下にあるが、差分の見張り（git）から外す。`sources_updated` では知らせない。
- ADR 0069
  - 例外: 外から届くものは `sources_updated` に寄せる方針のうち、本人のチャットのメッセージの添付は、置き場所だけを `/sources` に揃え、知らせはメッセージで行う。
- ADR 0008
  - 保つ: 添付のあるメッセージも、`conversation.send` で同じ 1 本の思考ループに 1 つの出来事として入る。
- ADR 0024
  - 保つ: 上げたファイルの ID はモデルに見せない。

### 進め方

1. この ADR。
2. natsumi: サーバー（上げる API、置き場所、メッセージへの添付、画像）とブラウザの画面を 1 つの PR にする。
   本番の Ingress が 25MB を通さなければ、その設定の変更を別に足す。

Mac・iPhone のアプリは、後で同じ API を使う。

## Consequences

- 本人は、ブラウザのチャットで資料や画像をなつみに渡せる。本文と添付は 1 つの出来事として届き、順序が入れ替わらない。
- 画像はメッセージと一緒にモデルに入るので、その分だけ文脈を使う。ほかのファイルは、なつみが読んだ分だけ文脈を使う。
- 上げたファイルは `/sources/uploads` に残り続け、data directory はその分だけ増え続ける。なつみからは消せない。
- `/sources` の下に、git の見張りの外にあるディレクトリが 1 つできる。`sources-diff` では見えない。
- cookie で状態を変える口が 1 つ増える。守りは、ログインの照合、`SameSite=Strict`、Origin の照合である。
- 上げるのは選んだ時点なので、送らなかったファイルも一度はサーバーに届く。片付けまでの間は残る。
- 同じ API を Mac・iPhone が使うには、アプリの側の作業が要る。
