# 0062. 返事の置き場所を、スレッド・チャンネル直下・チャンネルにも出すの 3 つから選ぶ

- Date: 2026-09-30
- Status: Accepted

## Context

ポッポさんは、natsumi が発言を指して返事を頼むと、置き場所を判定に聞く（[ADR 0039](0039-slack-as-files-and-a-scored-dove.md)、
[ADR 0059](0059-two-judges-side-by-side-and-fewer-issues.md)）。今の選択肢は 2 つである。

- `thread`: 返す相手の発言のスレッドにだけ返す（既定）。
- `channel`: スレッドに返し、チャンネルにも表示する（Slack の `reply_broadcast`。ADR 0059 のマージ後の追記）。

発言を指すと、返事は必ずそのスレッドに入る。チャンネル直下でやりとりが続いているときに、その流れのまま直下に返す手段が無い。
本人は、話の流れがどちらに向いているかで返す場所を決めたいと考えた。「特にその発言への返事」というのでなければ、
チャンネル直下の流れにはチャンネル直下に返したい。どこに返すかは、判定（Jev）に決めさせたい。

判定に見せる周りの発言も、返す相手の発言までで、スレッドかチャンネル直下のどちらか片方だけである。
流れがどちらに向いているか、スレッドが古くなっているかは、これでは分からない。

設計は grill-me（Q1〜Q10）で詰めた。

## Decision

### 置き場所は 3 つとし、値の名前を意味どおりに付け直す

| 値 | 置き場所 |
|---|---|
| `thread` | 返す相手の発言のスレッドにだけ返す（相手がスレッドの中の発言なら、そのスレッド） |
| `channel` | チャンネル直下のふつうの投稿。スレッドを作らない |
| `broadcast` | スレッドに返し、チャンネルにも表示する（Slack の `reply_broadcast`） |

- 今までの `channel`（スレッドに返し、チャンネルにも出す）は、`broadcast` に名前を変える。`channel` は、名前どおりチャンネル直下を指す。
- 返信先の無い投稿（チャンネルそのものへの投稿）は、今までどおり置き場所 `channel` で、チャンネル直下に出す。置き場所は判定に聞かない。

退けた案:

- **今の `channel` の名前を残し、直下に新しい名前を付ける**: 値を読むたびに「`channel` はチャンネル直下ではない」と読み替えることになる。
  値の名前を意味どおりにし、過去の記録は migration で書き換える。

### 判定に聞く基準

- 流れがチャンネル直下にあれば、既定は `channel` とする。返す相手がチャンネル直下の発言で、その周りでチャンネル直下のやりとりが続いていれば `channel` である。
- `thread` は、その発言にだけ向けた返事（質問への答え、頼まれたことの報告など）のときとする。
- `broadcast` は、古いスレッドへの返事で、チャンネルの皆に見せる意味があるものだけとする。
- 「古い」は、判定が発言の時刻と今の時刻から判断する。しきい値は置かない。チャンネルの賑やかさで、古さの感じ方は変わるからである。
- 返す相手がスレッドの中の発言でも、3 つとも選べる。流れがもうチャンネル直下に移っていれば、判定は `channel` を選べる。
- ADR 0059 の「置き場所の基準をスレッド寄りに書き直す」は、この基準で置き換える。

### 判定に見せる材料は、両方の流れを今の時点まで

- 判定に渡す state に、次のものを入れる。
  - 今の時刻（本人のタイムゾーン、秒まで）。
  - チャンネル直下の最新の発言（今の時点まで）と、その最後の発言の時刻。
  - 返す相手の発言のスレッドの最新の発言（相手より後の発言も含め、今の時点まで）と、その最後の発言の時刻。返信先の無い投稿では無い。
- 件数と 1 件あたりの文字数は、今までの `slack.judgeContext`（既定 5 件・500 字）を、チャンネル直下とスレッドのそれぞれに使う。
  設定を分けるほどの理由がまだ無い。
- 問題点の判定（[ADR 0059](0059-two-judges-side-by-side-and-fewer-issues.md) の 5 項目）も、同じ state を見る。
  Jev の 1 回の呼び出しは 1 つの state に全部の問いを載せるので、置き場所だけ材料を変えることはできない。
  また ADR 0040 の「2 つの方式は同じ問いと同じ材料を使う」を保つ。
  問題点の判定は、相手より後の発言と、もう一方の流れも見るようになる。答えた後の会話や別の流れに、下書きと食い違う事実や、既に聴かれたことが出てくることがあるので、見えて困るものではない。
  判定に送る発言の量は、最大で今の 2 倍になる。

### 判定が無いとき

- 決め方の順番は今までどおり、採用する方の判定 → もう一方の判定（[ADR 0059](0059-two-judges-side-by-side-and-fewer-issues.md)）→ サーバーの決まり、とする。
  Jev と logprobs の置き場所の問いは同じ 3 択とする。logprobs は選択肢に A・B・C の記号を振って聞く。
- サーバーの決まり（[ADR 0039](0039-slack-as-files-and-a-scored-dove.md)）は、中身を 3 択に読み替える。
  - 返す相手がスレッドの中の発言なら `thread`。
  - チャンネル直下の発言で、その後のチャンネル直下の発言が `slack.placementFollowing` 件以内なら `channel`（チャンネル直下）。超えたら `thread`。
  - `broadcast` は、判定があるときだけ選ばれる。サーバーの決まりでは選ばない。
- 今までの決まりで「チャンネル」になっていた場合（スレッドに返し、チャンネルにも出していた）は、チャンネル直下に出すことに変わる。

### 送り方

- `thread`: 返す相手のスレッドに返す。
- `channel`: `thread_ts` を付けずに、チャンネル直下に出す。
- `broadcast`: 返す相手のスレッドに `reply_broadcast` 付きで返す。
- 画像付きの投稿は、Slack のアップロード（`files.completeUploadExternal`）が `reply_broadcast` を受け付けない。
  - 画像付きの `broadcast` は、スレッドにだけ置く。チャンネル直下に出すと、古いスレッドへの返事が文脈から切り離されるからである。
  - 画像付きの `channel` は、チャンネル直下に出す。

### 承認と記録

- 承認の `target.placement` と、本人の決定（`approval.decide`）の `placement` は、3 つの値のどれかとする。
  承認の画面は、3 つから選び直せる。クライアントの契約（`docs/client-contract.md`「Slack の投稿の承認」）を改める。
- 承認の `reason.placement.probabilities` は、置き場所の値をキーにした確率とする。キーは 3 つ揃っているとは限らない
  （判定が確率を返さない場合や、この決定の前の記録）。クライアントは知らないキーを無視し、欠けたキーは無いものとして扱う。
- クライアントは、知らない置き場所の値に耐える。値が知らないものでも承認を表示し、承認・修正・却下ができる。
- 記録済みの値は、migration で新しい名前に書き換える。
  - 返信先のある投稿の置き場所・本人の決めた置き場所・承認の表示の置き場所の `channel` は `broadcast` にする。
  - 送った先（`sent_placement`）の `channel` は、画像の無い投稿だけ `broadcast` にする。画像付きの投稿はチャンネル直下に出ていたので、`channel` のままとする。
  - 置き場所の確率と、2 つの判定のそれぞれの答えに残った置き場所（選択と確率）の `channel` も、`broadcast` にする。
  - 返信先の無い投稿の `channel` は、そのままとする。もともとチャンネル直下を指していた。
- ダッシュボードの置き場所は、「スレッド」「チャンネル」「チャンネルにも」の 3 つの言葉で見せる。

### 確かめ方

- 事前の評価はしない。本番に入れて、ダッシュボードで 2 つの判定の置き場所を見比べる。
- 事前の評価（`probe:jev`）の置き場所の場面と、選択肢の順番を入れ替えて差を見る仕組みは、3 つの選択肢で動くようにする。

### 出す順番

- 承認を受けるアプリ（iPhone）を先に、3 つ目の値と知らない値に耐えるようにして出す。サーバーは、その後に本番に入れる。
  古いアプリに新しい値が届くと、承認の置き場所を読めないからである。

### ADR との関係

- ADR 0059
  - 置き換え: 置き場所を「スレッドかチャンネルか」の 2 択で聞くこと。3 択で聞く。
  - 置き換え: 置き場所の基準をスレッド寄りにすること。流れがチャンネル直下にあれば既定でチャンネル直下とする。
  - 置き換え: 置き場所「チャンネル」の意味（スレッドに返し、チャンネルにも出す）。この意味の値は `broadcast` とし、`channel` はチャンネル直下とする。
  - 置き換え: 判定なしのときに決まりで「チャンネル」になる場合は、スレッドに返してチャンネルにも出すこと。チャンネル直下に出す。
  - 置き換え: 画像付きの「チャンネル」はチャンネル直下に出すこと。画像付きの `broadcast` はスレッドにだけ置く（画像付きの `channel` は直下のまま）。
  - 置き換え: 承認の `placement` の値とクライアントの契約の形を変えないこと。値を 3 つにする。
  - 保つ: 2 つの判定を同時に掛けて採用する方で決めること。判定に渡す返信先の `in_thread`。
- ADR 0039
  - 置き換え: 判定に見せる周りの発言（返す相手の発言までの、スレッドかチャンネル直下の片方）。両方の流れを今の時点まで見せる。
  - 保つ: 判定なしのときにサーバーの決まりで置き場所を決めること。決まりの形（スレッドの中ならスレッド、チャンネル直下なら後の発言の件数で決める）。

## Consequences

- チャンネル直下でやりとりが続いているとき、なつみの返事がスレッドに埋もれず、流れのまま直下に出る。
- 古いスレッドに返すときだけ、チャンネルにも出る。
- 判定なしのときの決まりで直下に出ることになるので、今までスレッドにも残っていた返事が、スレッドには残らなくなる。
- 判定に送る発言が増える。logprobs の判定は prefill が増え、Jev はその分の料金が増える。
- 問題点の判定の材料も変わるので、この決定の前と後で点数の付き方が変わりうる。振り返るときは日付で分ける。
- 記録の置き場所の値が書き換わるので、この決定の前の記録も新しい意味で読める。
- 承認のクライアントは、サーバーより先に 3 つの値に対応しなければならない。

### 進め方

1. この ADR。
2. natsumi の実装: 判定の問いと材料、logprobs の 3 択、送り方、承認の受け口、ブラウザーの承認とダッシュボードの表示、migration、マニュアル・README・クライアントの契約。
3. iPhone アプリ: 3 つの値と知らない値に耐える承認画面。サーバーより先に出す。
