# 0035. 外のエージェントに頼むツールと、返事の受け取り方

- Date: 2026-09-24
- Status: Accepted（「まだ決めていないこと」の 2 点、頼める相手の名前をどこで知るかと返事を待ち続ける上限は [ADR 0036](0036-a-manual-to-read-and-a-limit-on-waiting.md) で決定、`agent_reply` の出来事に相手が返した画像の `images` と `images_not_taken` を足すことは [ADR 0048](0048-bringing-in-images-an-agent-hands-back.md) で追加）

## Context

[ADR 0025](0025-talking-to-outside-agents-over-a2a.md) で、なつみは外の特化エージェントに A2A で頼むことにした。
頼むのはツールで行い、ツールは受け付けたことだけを返し、返事は後からイベントとして思考ループのキューに入る。
context の ID はサーバーが持ち、モデルに写させない。

そのうえで、次の 3 つを決めずに残していた。

- 返事をどう受け取るか（流してもらう、知らせてもらう、取りに行く）
- 頼むツールの名前と引数
- 「前のやり取りに続けて頼む」か「新しく頼む」かを、ID を使わずにどう指定するか

最初の相手は `yuanying/fraction-agents` の Wiki 管理人である。Wiki 管理人は、メッセージを受けるとすぐに Task を返し、
その後の状態は Task を取りに行って（GetTask）知る形である。ストリーミングも push 通知も出していない。
答えの前に、エージェントが聞き返すこと（`INPUT_REQUIRED`）もある。

また、次の制約がある。

- なつみのバックエンドは prefill が遅い。system prompt とツールの定義は session の間は変えず、
  ツールの説明を設定の値から組み立てない（[ADR 0019](0019-a-workspace-not-a-memory-tool.md)）。
- 形の似た ID をモデルに写させる設計は、返事を落とした（[ADR 0024](0024-no-event-ids-for-the-model.md)）。
- 外のエージェントを呼ぶ token は、サーバーのコンテナにだけ見せる（[ADR 0033](0033-running-on-kubernetes.md)）。
  作業環境の外向きは全部拒否している（[ADR 0034](0034-an-allow-list-for-the-way-out.md)）。

本人からは、ツールではなく skill と A2A の CLI を作業環境で使わせるほうが、なつみのモデルにとって使いやすいのではないか、という問いがあった。

## Decision

### 頼むツールは汎用の 1 つ

- ツールは `ask_agent` の 1 つとする。相手ごとにツールを作らない。
  相手が増えるたびにツールの定義が変わり、prefix cache が壊れるためである。
- 引数は次の 3 つである。

| 引数 | 意味 |
| --- | --- |
| `agent` | 相手の名前 |
| `message` | 頼む文面 |
| `continue` | その相手との直近のやり取りに続けるかどうか |

- 相手の名前は設定で持ち、サーバーが確かめる。設定に無い名前は、頼まずに断る結果を返す。
  相手の URL や認証は設定の側にあり、モデルは名前しか扱わない。
- `continue` を真にすると、サーバーはその相手との直近の context に続けて送る。偽なら新しい context で始める。
  - サーバーは、相手ごとに直近の context を覚えておく。モデルは context の ID を見ず、写さない（ADR 0025、ADR 0024）。
  - エージェントの聞き返し（`INPUT_REQUIRED`）への答えも、`continue` を真にした `ask_agent` で返す。
    答えるための別のツールは作らない。
- ツールは受け付けたことだけをすぐに返す。結果の文には、返事が後でイベントとして届くことを書く（ADR 0025 のまま）。
- ツールの説明は固定の文にする。設定にある相手の一覧から文面を組み立てない（ADR 0019 の規則）。

### skill と CLI にしなかった理由

- CLI を作業環境で動かすには、作業環境に外への出口と、呼び出しの token を渡すことになる。
  出口は今は全部拒否しており（ADR 0034）、token は作業環境に見せないと決めている（ADR 0033）。
  ADR 0004 の「任意 HTTP を許可しない」、ADR 0025 の「エージェントとのやり取りはサーバーを通す」にも反する。
- エージェントの返事には時間が掛かる。CLI で待つなら、`run_shell` の応答の上限を超える長い待ちになる。
  待たずに返すなら、後で結果を取るために、Task の ID をモデルに写させることになる（ADR 0024 の問題）。
- ツールなら、返事はほかのイベントと同じ形で届き、なつみは待つ間も他のことができる。
- なつみのモデルで、ツールと CLI のどちらが使いやすいかは実測していない。

### 返事はサーバーが取りに行く

- サーバーは、返事を待っている Task を、定期的に（例: 15 秒ごとに）GetTask で取りに行く。
  相手がストリーミングも push 通知も出していないので、取りに行く形が相手を変えずに使える唯一の方法である。
  `yuanying/fraction-agents` の側は変えない。
- Task が次のどれかになったら、イベントとして思考ループのキューに入れる。
  - 完了: 返事の文面を載せる。
  - 失敗: 失敗したことを載せる。
  - 聞き返し（`INPUT_REQUIRED`）: エージェントが聞いていることを載せる。なつみは `ask_agent` の `continue` で答える。
- イベントには相手の名前を付ける。Task や context の ID はモデルに見せない。
- 待っている Task は SQLite に記録する。サーバーが再起動しても、記録から取りに行き直す。返事を黙って落とさない。
- 相手が将来ストリーミングや push 通知を出すようになったら、受け取り方を変えるかはそのときに決める。

### 置き換える既存の決定

- ADR 0025
  - 決定:「まだ決めていないこと」のうち、返事の受け取り方、なつみが頼むツールの名前と引数、
    前のやり取りに続けるか新しく頼むかの指定の 3 つ。
  - 残す: 受け口の上限と公開先、エージェントとのやり取りを Mac に見せるか、画像を Mac に出すか。まだ決めていない。
  - 残す: A2A の版と SDK は、実装の作業単位の着手時に確かめる。

### まだ決めていないこと

- なつみが、頼める相手の名前をどこで知るか。ツールの説明には一覧を書かない。
- 返事を待ち続ける上限。相手が完了も失敗も返さないまま長く止まったときに、いつ諦めてなつみに知らせるか。

## Consequences

- 相手が増えても、ツールの定義は変わらない。増やすのは設定だけである。
- 続けられるのは、相手ごとに直近の 1 つのやり取りだけである。同じ相手と 2 つのやり取りを並べて続けることはできない。
  新しく頼めば、前のやり取りには戻れない。
- 返事は、取りに行く間隔の分だけ遅れて届く。待っている Task が多いほど、相手への問い合わせが増える。
- 待っている間、サーバーは相手に問い合わせ続ける。相手が止まっていれば、問い合わせは失敗し続ける。
- なつみのモデルは、聞き返しに答えるときに `continue` を真にし忘れることがある。忘れると、新しいやり取りとして届き、相手は聞き返しの文脈を持たない。
