# 0044. なつみは作業環境の sdctl で画像を作り、ポッポさんへの依頼で Slack に投稿する

- Date: 2026-09-26
- Status: Accepted（2026-09-26: sdctl の既定を image の設定ファイルに置くことを「追記」の節に加えた。未決としていた画像を Mac に出すかと、画像を取る道が会話の行の画像も返すことは [ADR 0045](0045-showing-the-owner-images-with-a-reply.md) で決定、既定の params を作業環境の image に焼き込む点は [ADR 0057](0057-an-avatar-directory-named-in-the-server-config.md) で置き換え（サーバーが書き、作業環境の `/manual/avatar` で読む）、依頼の見出し `画像` は [ADR 0074](0074-asking-poppo-in-json-and-hearing-back-in-sources.md) で置き換え（JSON の `images` の欄））

## Context

本人は、なつみに画像を作らせ、投稿させたいと考えた。投稿先は、最初は Slack だけでよい。
[ADR 0039](0039-slack-as-files-and-a-scored-dove.md) は、画像の受け取りを決め、画像の投稿を後日の範囲としていた（実装の順の 4 番目）。

手元には次のものがあった。

- 本人の画像生成サーバーで、AUTOMATIC1111 の Stable Diffusion WebUI（以下 sd-webui）が動いている。
  その前には認証の proxy があり、ブラウザでないクライアントは bearer token で通る。
- sd-webui を shell から使う CLI の sdctl がある。本人も使っている。接続先は環境変数 `SDCTL_URL` で指すだけで、認証のヘッダを付ける仕組みは無い。
- なつみの作業環境には shell（`run_shell`）があり、ツールを増やさずにコマンドで道具を足してきた（[ADR 0019](0019-a-workspace-not-a-memory-tool.md)、ADR 0039 の `view`）。
- 作業環境の外向きは、名前解決も含めてすべて拒否している。loopback は通る（[ADR 0034](0034-an-allow-list-for-the-way-out.md)）。
- 同じ Pod の出口の proxy は nginx の stream モジュールで、TLS の SNI を見て振り分けるだけで、TLS を解かない（ADR 0034）。
  そのままでは、通る要求に HTTP のヘッダを付けられない。
- ポッポさんへの依頼は見出し付きのテキストで、本文のある投稿は判定に掛ける（ADR 0039、[ADR 0040](0040-the-dove-sends-what-the-judge-passes.md)）。
  判定のモデルは画像を見られない。
- 本人の承認は iPhone で行う（[ADR 0041](0041-approving-slack-posts-on-the-iphone.md)）。承認は、作った時点の中身で固定する（ADR 0040）。

[ADR 0025](0025-talking-to-outside-agents-over-a2a.md) は、画像生成を、なつみの外の特化エージェントの例に挙げていた。

## Decision

### 生成は作業環境の shell で sdctl を使う

- なつみは、作業環境の shell で sdctl（`sdctl txt2img` など）を使って画像を作る。ツールは増やさない。
- sdctl は作業環境の image に入れる。版は固定する。
- 作った画像は `/work` の下に置く。なつみは `view <パス>` で自分の作った画像を見られる（ADR 0039）。
- 画像生成を外の特化エージェントにする形（ADR 0025 の例）は取らない。sdctl がすでにあり、ツールも A2A の相手も増やさずに済むからである。

### sd-webui への道は、出口の proxy の中継で token を付ける

- 作業環境の外向きの拒否は、今のまま保つ。名前解決も与えない。
- 出口の proxy（nginx）に、平文の HTTP を loopback で受ける中継を足す。
  - 行き先は、本人の画像生成サーバーの 1 つに設定で固定する。要求の中身から行き先を変えない。
  - 中継は、行き先への TLS の証明書を検証し、`Authorization` のヘッダに bearer token を付けて送る。
  - token は秘密として proxy のコンテナにだけマウントする。作業環境からもサーバーからも読めない。
  - 作業環境の `SDCTL_URL` は、この中継の loopback のアドレスを指す。
- 今の SNI の振り分けに足さないのは、TLS を解かないのでヘッダを付けられないからである。
  中継は同じ nginx の中の別の口（http の server）とし、SNI の振り分けはそのまま残す。
- token を作業環境に置かないので、なつみは中継が通す API の外で sd-webui や認証の proxy を使えない。

### 中継が通す API

| 通す | 方法 | 用途 |
| --- | --- | --- |
| txt2img・img2img | POST | 生成 |
| progress | GET | 進み具合 |
| モデル・sampler・scheduler・モジュール・upscaler の一覧 | GET | 使えるものを知る |
| options | GET | 今の設定を読む |

- ほかの道と方法は、中継が断る。
- options への POST（sd-webui 全体のモデルや設定の書き換え）は止める。sd-webui は本人も使っており、全体の設定を変えると本人の生成にも効いてしまうからである。
- モデルは、生成の要求ごとの override で指定する。sd-webui 全体の既定のモデルは変えない。

### 画像の指定は、ポッポさんへの依頼の見出し

- ポッポさんへの依頼（ADR 0039 の見出し付きテキスト）に、見出し `画像: <パス>` を足す。例は `画像: /work/images/cat.png`。
  - 複数枚なら、見出しの行を重ねる。
  - パスは作業環境から見たものを書く。サーバーは、作業環境の `/work` をサーバーの側の同じ場所に読み替える。
- 画像に使えるのは `/work` の下のファイルだけとする。`/work` の外を指すもの（`..` やリンクで外に出るものを含む）は断る。
- サーバーは、形式（PNG・JPEG・WebP）と大きさを検査する。合わなければ頼まずに、直し方を添えて突き返す（ADR 0040 の見出しの検査と同じ扱い）。
- 依頼を受けた時点で、サーバーは画像を作業環境から書き換えられない場所に写す。承認でも送信でも、使うのはこの写しである。
  `/work` のファイルが後で書き換わっても、本人が承認した画像と送る画像がずれない（承認画面の節）。
- 本文があれば、それを画像のコメントとして画像と一緒に投稿する。
- Slack には `files.uploadV2` で上げる。置き場所（スレッドかチャンネルか）は、本文があれば判定が選び（ADR 0040）、
  画像だけならサーバーの決まり（判定なしのときと同じ、ADR 0039）で決める。

### 判定は本文だけ

- 本文があれば、これまでどおり判定に掛ける。判定の材料に画像は入らない。判定のモデルは画像を見られないからである。
  判定が「送る」なら画像と一緒に自動で送り、「本人に回す」なら画像ごと承認に回す。
- 画像だけ（本文なし）の投稿は、判定にも本人の承認にも通さずに送る。本文を書かないリアクション（ADR 0039）と同じ扱いである。
- 画像の中身は検査しない（ADR 0039 のまま、本人の判断）。
- なつみは生成ごとの override で、本人の画像生成サーバーにあるどのモデルも選べる。意図しない画像も作れる。
  モデルは最初は絞らない。意図しない画像が出たら考える（本人の判断）。

### 承認の画面に画像も見せる

- 承認に回った投稿では、本人に画像も見せる。承認の中身には、依頼の時点で写した画像も含める。
- サーバーは、承認の API に、承認待ちの画像を取る道を足す。ログインが要る。承認に結び付いた写しの画像だけを返す。
- iPhone の承認画面で画像を並べるのは、別の作業として本人が進める。サーバーと iPhone の形は `docs/client-contract.md` に書く。

### 生成の回数は、当面絞らない

- 生成の回数に上限を設けない。思考ループのモデル呼び出しの回数の上限が、間接的に効く。
- 本人の画像生成サーバーの GPU は、本人自身の利用やほかのサービスと共有している。運用で、生成が混み合って本人の利用や他のサービスに響かないかを見て、必要になったら上限を決める。

### 作り方は /manual の手引きで知る

- sdctl の使い方と、モデルごとのプロンプトの書き方を、`/manual` に手引きとして置く（[ADR 0036](0036-a-manual-to-read-and-a-limit-on-waiting.md)）。
  プロンプトの書き方は、本人が画像生成に使っている手引きを要約する。
- 既定の生成の設定（params）を作業環境に用意する。モデルは Anima 系のもの、Negative prompt 付きとする。
  なつみは基本的に、この既定の設定を使ってプロンプトだけを書けばよい。
- なつみ本人の姿を描くための LoRA と、姿を出すためのプロンプトの書き方を、手引きに書く。
- 手引きを足しても、system prompt とツールの定義は変わらない（ADR 0036）。

### 置き換える既存の決定

- ADR 0039
  - 決定:「画像の投稿は後日の範囲」。ポッポさんへの依頼の `画像` の見出しで投稿する。
  - 残す:「画像の中身は検査しない」。ただし、前提にしていた「なつみは意図しない画像を作れない」は、この ADR で崩れる（Consequences）。
- ADR 0040
  - 追加: 依頼の見出しに `画像`。画像だけの投稿は、判定にも承認にも通さずに送る。
- ADR 0041
  - 追加: 承認の画面に画像を見せる。サーバーは承認待ちの画像を取る道を持つ。
- ADR 0034
  - 追加: 出口の proxy に、loopback で平文の HTTP を受け、行き先を固定して token を付ける中継を足す。作業環境の UID の外向きの拒否は変えない。
  - 残す: SNI の振り分けは TLS を解かない。
- ADR 0025
  - 置き換え: 画像生成を外の特化エージェントにする例。画像の生成は作業環境の sdctl で行う。
  - 残す: 画像を Mac に出すか。この ADR でも決めない（投稿先は Slack だけ）。

## Consequences

- なつみは、shell の中で画像を作り、見て、作り直してから投稿できる。ツールの定義も system prompt も変わらないので、prefix cache は壊れない。
- 作業環境から、loopback の中継を通して本人の画像生成サーバーに届く道ができる。外へ出る道はこの 1 本だけで、行き先も通す API も中継が固定する。
  sshd でログインするユーザーの UID からも、同じ中継に届く。
- ADR 0039 が前提にしていた「なつみは意図しない画像を作れない」は、もう成り立たない。モデルを絞らないので、画像生成サーバーにあるどのモデルでも描ける。
  画像の中身は検査しないので、なつみが作った画像は、画像だけの投稿なら本人も判定も見ないまま Slack に出る。
  参加させるのが漏れてよいチャンネルだけであるという、テストの段階の前提（ADR 0039）で受け入れる。
  意図しない画像が出たら、中継で要求の中のモデルの指定を許可リストで見る、画像だけの投稿を承認に回す、などを見直しの候補とする。
- token は proxy のコンテナの秘密として増える。本人が認証の proxy で発行し、環境の設定に入れる。
- options への POST を止めるので、なつみは sd-webui 全体の既定のモデルを変えられない。モデルを変えるときは、生成ごとの override で指定する。
- 生成の回数を絞らないので、なつみが生成を繰り返すと、本人の画像生成サーバーの GPU を取り合う。混み具合は運用で見る。
- 依頼の時点で画像をサーバー側に写すので、写しの分だけ data directory が増える。
- iPhone の承認画面で画像が見えるまでは、承認に回った画像付きの投稿は、画像を確かめられないまま承認することになる。
- 手引きの既定の設定とモデルは image に焼くので、変えるには image を作り直す。

作業は次の単位で進める。

1. natsumi: 作業環境の image に sdctl と既定の設定、`/manual` の手引き、依頼の `画像` の見出しの検査と写しと `files.uploadV2`、承認の API の画像
2. 環境の設定（private のリポジトリ）: 出口の proxy の中継（通す API はこの ADR の表）、token の秘密、作業環境の `SDCTL_URL`

1 と 2 は並行して進める。iPhone の承認画面の画像と、token の発行は本人が行う。

## 追記（2026-09-26）: sdctl の既定は image の設定ファイルに置く

- 作業環境の runner は、コマンドに `PATH`・`HOME`・`LANG`・`TZ` しか渡さない（[ADR 0019](0019-a-workspace-not-a-memory-tool.md)）。
  このため、コンテナの環境変数 `SDCTL_URL` も、image の環境変数の既定の設定と出力先も、なつみのコマンドには届かず、sdctl は既定の接続先（`localhost:7860`）へつなごうとして失敗した。
- runner の環境の規則は変えない。sdctl の接続先・既定の設定・出力先は、image の設定ファイル（`/etc/sdctl/config.yaml`）に置く。
  PATH の `sdctl` は、本物の sdctl にいつもこのファイルを渡すラッパーとする。どのシェルから使っても同じ既定になる。
- 接続先は中継の loopback のアドレス（`127.0.0.1:17860`）を image に書く。環境の設定の約束と同じ値であり、変えるときは両方を直す。
  「作業環境の `SDCTL_URL` は、この中継の loopback のアドレスを指す」は、コンテナのシェル（本人の `kubectl exec` など）のための値として残る。sdctl では環境変数が設定ファイルより勝つが、値は同じである。
- 既定を本人の HOME（永続領域）の下に置く形は取らない。image の版と既定の版がずれるからである。
