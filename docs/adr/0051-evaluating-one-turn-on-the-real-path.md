# 0051. 本物のターンの経路で 1 ターンを回し、場面ごとの成功率で評価する

- Date: 2026-09-27
- Status: Accepted（評価で回せるものに、写しから始める整理係の一晩（全工程）を加えることは [ADR 0068](0068-a-curator-that-remembers-like-a-person.md) で追加）

## Context

プロンプト、マニュアル、イベントの形、ツールを変えたとき、なつみがその変更どおりに動くかを確かめたい。
一度動けば済むのではなく、同じ場面を何度も回して、どのくらいの割合で期待どおりに動くかを知りたい。

これまでの評価（思考ループの評価、`sources_updated` の読み方の評価など）は、どれも使い捨てのハーネスだった。
プロンプトとマニュアルを写し、ツールを作り直していたので、natsumi の本物のコードの経路は通っていない。
写しが本物からずれれば、評価の結果もずれる。
ソースの変更（イベントの行の作り方、ツールの結果の文、workspace のコマンド）は、写しを直さない限り評価に入らない。

手元の事情は次のとおりである。

- 1 ターンの中身は、思考ループ（[ADR 0008](0008-single-thinking-loop-and-mac-conversation.md)）の `runTurn` が決める。
  イベントの行、システム指示、ツールの定義と結果の文、ターンの打ち切り（呼び出し回数と時間）がここにそろっている。
- 思考ループには、差し替えの口がすでにある。モデルの実行環境、Pi の session を作った直後に呼ばれる関数、外のエージェントの client、Slack とポッポさんの側である。
- workspace の shell は、runner に Unix socket 越しに命令を送る（[ADR 0019](0019-a-workspace-not-a-memory-tool.md)）。runner は Go の小さなプログラムで、閉じ込めはコンテナの形が担う。
- マニュアルはリポジトリの `manual/` で、workspace には `/manual` として見える（[ADR 0036](0036-a-manual-to-read-and-a-limit-on-waiting.md)）。
- モデルには ID を見せない（[ADR 0024](0024-no-event-ids-for-the-model.md)）。評価も、この形のまま測らなければ意味がない。
- モデルの経路は、本番の設定の `pi` の書き方で決まる（[ADR 0046](0046-named-model-routes-switched-by-hand.md)）。key はファイルか環境変数から読み、表示しない。
- リポジトリは public である。本番の会話や記憶を入れることはできない。

設計は grill-me（Q1〜Q5 と細部の既定）で詰めた。

## Decision

### 本物のターンの経路をそのまま通す

- 評価の仕組みは natsumi のリポジトリに置く。サーバーと同じ思考ループを開き、そこに出来事を 1 つ渡して、1 ターンを回す。
  システム指示、ツールの定義、ツールの結果の文、イベントの行、打ち切りは、すべて評価するブランチの本物である。
  プロンプトだけでなく、ソースの変更もそのブランチのまま評価できる。
- 差し替えるのは外への作用だけである。
  - Mac への返事と知らせは、思考ループが SQLite に書く行と、クライアントへのイベントをそのまま記録する。つなぐ端末はない。
  - ポッポさんへの依頼は、本物の依頼の読み取りで形を確かめ、受け付けの文を返して記録する。Slack には何も送らない。
  - APNs、Slack、外のエージェントにはつながない。
- 差し替えは依存の注入で行う。本番のコードには評価のための分岐を置かない。
  足すのは、システム指示の文を差し替える口の 1 つだけである（下の「変種」）。これも注入で、渡さなければ何も変わらない。
- 1 回ごとに新しいデータディレクトリ、新しい SQLite、新しい Pi の session で回す。回どうしで何も持ち越さない。
- ターンの後の一行メモ（[ADR 0047](0047-folding-ended-turns-with-a-memo.md)）は、既定では評価するモデルに頼まず、決まった文で答える。
  評価したいのはターンそのものであり、メモの呼び出しは 1 回ぶん費用と時間がかかるからである。メモも評価したいときは指定で本物に回せる。

退けた案:

- **プロンプトとツールを写したハーネスを作る**: これまでのやり方である。写しがずれ、ソースの変更が評価に入らない。
- **本番のサーバーをまるごと起動して WebSocket から話しかける**: TLS、ログイン、スケジューラー、Slack の接続まで要り、場面の始めの状態も作りにくい。1 ターンを測るのに要らないものが多い。

### workspace の shell は、本物の runner を bubblewrap の中で動かす

- runner はリポジトリの Go のソースからその場で組み立て、bubblewrap（bwrap）の中で動かす。
  本番の作業環境の image にも Docker にも頼らず、手元で動く。
- bwrap の中の配置は、本番のコンテナに合わせる。`/memory`（`.git` は読み取り専用）・`/work`・`/home/natsumi` は回ごとのディレクトリで書ける。
  `/manual` はリポジトリの `manual/` の写し、`/manual/agents` と `/sources` は回ごとのディレクトリで、読み取り専用である。
  image が `/usr/local/bin` に置くスクリプトは、Dockerfile のその行を読んで同じ場所に置く。ネットワークは切る。
- コマンドは手元の `/usr` のもので動く。本番の image と道具の版が違うことはある。
- bwrap が使えない環境（CI など）のために、runner を閉じ込めずに手元で動かす形も持つ。
  パスが本番と違い、閉じ込めもないので、偽のモデルでの動作確認にだけ使う。実モデルの評価では使わない。

退けた案:

- **本番の作業環境の image を Docker で動かす**: 本番と同じ道具になるが、image の build と Docker が要り、手元で気軽に回せない。
- **runner を TypeScript で書き直す**: 応答の上限や出力の上限の振る舞いが本物からずれる。

### 場面は YAML で書き、部品で足りない判定だけ TypeScript の関数にする

- 1 つの場面は、1 つのディレクトリの YAML である。書くのは次のものである。
  - 始めの状態: workspace のファイル（`/memory`・`/sources`・`/work`・`/home/natsumi`、マニュアルの差し替え）、時刻、前置きのやりとり、文脈の水増し。
  - 渡す出来事: 本人のメッセージ、ping、または出来事の行そのもの。
  - 判定の項目、回数、打ち切り、変種。
- 出来事は 2 つの形で渡せる。
  - 本人のメッセージと ping は、サーバーと同じ入口から渡す。行は本物のコードが作る。
  - 出来事の行そのものを書く形も持つ。まだ無いイベントの形や、同じイベントの欄の違いを比べるためである。行はサーバーの出来事の口（Slack の側など）を通して渡すので、ターンの経路は同じである。
  - 生の Slack のメッセージから行を組み立てる形は、今は持たない。必要になったら足す。
- 場面は、要る機能を名前で書ける。評価するブランチにその機能が無ければ、その場面は飛ばして、飛ばしたことを集計に残す。
- 変種は、同じ場面の小さな違いである。出来事、ファイル、ファイルの一部の書き換え、システム指示の一部の書き換え、判定の項目を変えられる。
  システム指示の書き換えは、書き換える文がブランチの指示に無ければ誤りとして止まる。気づかずに変種が元と同じになることを防ぐためである。
- 前置きのやりとりは、決まった応答を返す偽のモデルで、本物の思考ループに回す。session も SQLite も、本番で前のターンがあったときと同じ形になる。
  そのあと評価するモデルに切り替えて、評価するターンを回す。

### 判定は規則を主にし、規則で書けない項目だけ LLM がルーブリックで判定する

- 規則の部品を用意する。ツールが呼ばれた・呼ばれなかった、shell のコマンドが正規表現に合う、ツールの出力に文字列が含まれる、あるファイルを読んだ・読まなかった、依頼の宛先と返信先、返事の文、呼び出し回数の上限、ターンが打ち切られずに終わった、などである。
- 部品で足りない判定は、場面の横の TypeScript の関数で書く。関数は、その回の記録を受け取って合否と理由を返す。
- 返事の質のように規則で書けない項目は、LLM がルーブリックで判定する。
  判定役は、評価するモデルと同じ「Pi の経路」の書き方で指定する。既定は ChatGPT Plus の経路（`openai-codex` の `gpt-6-sol`）である。
  判定役に見せるのは、渡した出来事、ツールの呼び出しと結果（長いものは切る）、返事である。
- 項目ごとに、規則・関数・LLM のどれで判定したかを記録に残す。判定できなかった項目（判定役の誤りなど）は、合否に数えず、そう記録する。
- 成功率は、場面・変種・項目ごとの N 回中の合格数と、Wilson の 95% 信頼区間で出す。
  副指標として、モデルの呼び出し回数、所要時間、トークン、打ち切りの回数を出す。

### 評価するモデルは本番の設定と同じ書き方で指定し、key を残さない

- 評価するモデルは、本番の設定の `pi` と同じ書き方のファイルで指定する（`pi.model`、互換エンドポイントなら `pi.compatible` の `baseUrl` と `apiKeyFile`）。
  経路の組み立ては本番と同じ関数を使う。
- key は表示せず、結果にも残さない。結果に残すのはモデルの provider と名前だけで、エンドポイントの URL も残さない（内部のホスト名であり得るため）。
- 打ち切りは本番と同じ思考ループの打ち切り（呼び出し回数と時間）である。場面か実行時の指定で変えられる。

### 結果はリポジトリの外か Git が無視するディレクトリに置き、版ごとに回して並べる

- 結果は、1 回ごとの JSONL と、集計表（Markdown と JSON）である。置き場の既定は Git が無視するディレクトリで、指定でリポジトリの外にも置ける。
  JSONL には、渡した出来事、ツールの呼び出しと結果、返事、判定、数値を入れる。session の写しも回ごとに残す。
- 2 つの版は、それぞれのブランチで回した結果を並べて比べる（`compare`）。場面・変種・項目ごとに、成功率の差と、その 95% 信頼区間（Newcombe の方法）を出す。
  ref を受け取って両方を回す形は、手間に感じてから、この上に薄く足す。
- CI では実モデルを回さない。`npm test` には偽のモデルでのドライランを入れ、ターンが本物の経路で走り、shell が実際に動き、判定・集計・比較が出ることを確かめる。

### 本番の文脈は「私的な場面」から読む

- リポジトリの場面は架空のものだけにする。
- 本番の文脈で試したいときは、リポジトリの外の「私的な場面」のディレクトリを指定する。
  そこに本番の Pi の session の写しを置けば、それを始めの文脈にして評価するターンを回せる。記憶の写しも置ける。
- 写しは本人が本番から取り出して置く。評価の仕組みは本番に触れない。取り出しの手順は README に書く。

## Consequences

- プロンプト、マニュアル、ツール、イベントの形の変更を、そのブランチのまま同じ場面で測り、前の版と成功率で比べられる。
- 思考ループの差し替えの口が、評価の仕組みの前提になる。口の形を変えるときは、評価の仕組みも合わせて直す。
- 手元の道具で動かすので、本番の image にしか無い道具を使う場面は、手元にその道具が要る。
- 実モデルでの評価は、回数ぶんモデルの利用枠を使う。判定役を Plus にすると、その上限も評価の回数ぶん減る。
- 出来事の行を直接書く場面は、サーバーが作る行と食い違い得る。サーバーが作れる出来事は、本人のメッセージや ping のように本物の入口から渡すほうがよい。
