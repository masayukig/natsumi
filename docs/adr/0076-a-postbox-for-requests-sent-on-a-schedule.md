# 0076. 郵便ポスト: 記憶に投函した定期便を、サーバーが cron で外のエージェントに送る

- Date: 2026-10-11
- Status: Accepted（返事を置いた回のディレクトリが、初めて見るディレクトリとして黙って取り込まれ、既定のふつうの更新が出ていなかった。動いている間に新しく現れたディレクトリもふつうの更新として出すことを [ADR 0050](0050-telling-of-source-updates-with-one-event.md) の 2026-10-12 の追記で決め、この ADR の「知らせの強さ」のとおりに出るようになった）

## Context

natsumi は外のエージェントに `ask_agent` で頼める（[ADR 0035](0035-asking-outside-agents-and-hearing-back.md)）。
返事はサーバーが `/sources/agents/<相手>/<日時>-<印>/` に置き、`sources_updated` の attention で知らせる（[ADR 0069](0069-agent-replies-as-files-in-sources.md)）。
ただし頼むのは、いつもなつみのターンの中である。毎朝のメールの確認のような決まった依頼でも、なつみが自分で予約した確認（[ADR 0063](0063-repeating-self-checks-without-limits.md)）で起き、
ターンを使って `ask_agent` を呼ぶ必要がある。予約を入れ忘れれば止まり、依頼のたびにモデルを呼ぶ。

本人は、ニュースを集める係を外のエージェントとして立てることにした。そのうえで、なつみが頼まなくても、ニュースが `sources_updated` で届くようにしたいと考えた。
さらに、これをニュースに限らず一般化したいと考えた。外のエージェントへの定期的な依頼を natsumi に用意しておき、サーバーが時刻どおりに送る。
メールや予定の確認も、毎回なつみが頼む必要はない。本人はこれを「郵便ポスト」と呼び、投函はツールではなくファイルで行うことにした。

手元には次のものがあった。

- 外から届くものは、可能な限り `sources_updated` に寄せる方針がある（ADR 0069）。返事の置き場所と知らせ方は、そのまま使える。
- 返事の構造のある形（reply/v1 の DataPart。`summary`・`sections`・`sources`）の取り決めが、`yuanying/fraction-agents` にある。
- 記憶は git のリポジトリで、なつみの書き込みはターンの終わりにサーバーが検査してからコミットする（[ADR 0018](0018-memory-in-git-and-the-nightly-rebuild.md)・[ADR 0020](0020-limits-at-write-time-and-a-nightly-menu.md)）。
  本人は ssh で自分でコミットでき、そのコミットは検査を通らない（[ADR 0067](0067-the-owner-commits-memory-over-ssh.md)）。
- 予約の時計は毎分見回り、cron 式を本人のタイムゾーンで読む部品がある（ADR 0063）。
- [ADR 0003](0003-assistance-and-integrations.md) は「Gmail と Calendar を 15 分ごとに確認する」と決めていたが、natsumi のサーバーには実装されていない。
  メールの確認は、読み取り専用の外のエージェントに `ask_agent` で頼む形になっており、natsumi に Gmail に固有のコードは置かないことにしている。

細部は本人との問答で決めた。

## Decision

### サーバーが cron で、モデルのターンを経ずに A2A の依頼を送る

- 郵便ポストは、サーバーの部品である。定期便の時刻が来たら、サーバーが相手に A2A の依頼を送る。なつみのターンは使わず、モデルも呼ばない。
- 返事の置き場所は `ask_agent` と同じ `/sources/agents/<相手>/<日時>-<印>/` とし、`sources_updated` で知らせる。ディレクトリの形・DataPart の検証・文章の返事を節に切ること・画像の取り込みは ADR 0069 のままとする。
- 定期便から送ったことが分かるように、`request.md` と、知らせの attention の `details` に `postbox: <定期便の名前>` を載せる。
  - attention を出さない回（次の「知らせの強さ」のふつうの更新）は、出来事に載るのは変わったディレクトリだけである。定期便の名前は `request.md` で分かる。
- 送るのは汎用の A2A の依頼である。natsumi は相手が何の係かを知らず、Gmail・Calendar・ニュースのどれにも固有のコードを持たない。
- 退けた案:
  - **相手から natsumi に push する**: natsumi に外からの受け口と、その認証が増える。今は natsumi から頼んで取りに行く向きだけである。
  - **相手と共有のボリュームに置く**: natsumi と相手の配置が結びつく。相手を別のクラスタや他人のエージェントにできなくなる。

### 投函は記憶の `postbox/*.md` で、サーバーは HEAD にコミットされた内容だけを読む

- 定期便は、記憶のリポジトリの `postbox/` の直下に置く Markdown のファイルである。
- サーバーは作業ツリーではなく、**HEAD にコミットされた内容**（`HEAD:postbox/`）だけを読む。
  - なつみの書き込みは、ターンの終わりの検査を通ってコミットされたものだけが定期便になる。書きかけのファイルを拾わない。
  - 本人の ssh のコミットも、コミットした時点で定期便になる。
- 読み直すのは HEAD が変わったときである。
  - ターンの終わりに、サーバーが記憶をコミットした直後。
  - 予約の時計の毎分の見回りで、HEAD の SHA が前に読んだものと違うとき。本人の ssh のコミットと、夜の整理係のコミットはこちらで拾う。
  - サーバーの起動時。
- 作業ツリーを fsnotify などで見張らない。作業ツリーの変化は、検査を通る前のものだからである。
- `/work` には置かない。`/work` は検査もコミットもされないので、正本にできない。
- `/sources` にも置かない。`/sources` はサーバーだけが書き、なつみからは読み取り専用である。

### ファイルの形

1 通 1 ファイルとする。例（架空）:

```markdown
---
to: news
cron: "0 7 * * *"
notify: attention
---
今朝のニュースから、ソフトウェアの開発と自宅のサーバーの運用に関わるものを選んでください。
同じ話題は 1 件にまとめ、5 件までにしてください。
```

| 項目 | 中身 |
| --- | --- |
| ファイル名 | 定期便の名前（`morning-news.md` なら `morning-news`）。返事の `details` と `request.md`、ダッシュボードの表示に使う |
| `to` | 送る相手。設定の `a2a.agents` の名前 |
| `cron` | 送る時刻。5 項目の cron 式 |
| `paused` | 省略できる。`true` なら送らない |
| `notify` | 省略できる。`attention` なら返事のたびにすぐ知らせる（次の節） |
| 本文 | 相手に渡す自然文の依頼 |

- 1 通 1 ファイルにするのは、1 件の誤りがほかの定期便に波及しないようにするためである。記憶の検査の「`.md` だけ」にも合い、skill（[ADR 0073](0073-skills-from-the-owner-and-her-own.md)）と同じく frontmatter と本文の形になる。
- やめるときは、ファイルを消す。一時的に止めるときは `paused: true` にする。
- cron 式は、予約の時計と同じ部品で読む。書き方と、本人のタイムゾーン（`loop.timeZone`）で読むことは ADR 0063 と同じである。

### 不正な投函は、なつみの書き込みなら検査で戻し、本人のコミットなら読むときに飛ばす

- なつみが `postbox/` に書いたものは、ターンの終わりの検査（ADR 0018・ADR 0020）で確かめる。当たったファイルは直前のコミットの状態に戻し、理由を次のターンの入力に添える。今の検査と同じ流れである。
- 検査の項目は次のとおりである。
  - frontmatter が YAML として読めること。
  - `cron` が正しい式であること。当てはまる時刻が一度も来ない式も当たる。
  - `to` が設定の `a2a.agents` にある相手であること。
  - `cron` の回の間隔が下限（後の「頻度と止め方」）より短くないこと。
- 本人の直接のコミットは検査を通らない（ADR 0067）。サーバーは HEAD から読むときに同じ項目を確かめ、通らない定期便だけを飛ばす。
  飛ばしたことと理由は、なつみとダッシュボードに見せる。ほかの定期便は送る。
- 起動した後に設定から相手が外れたときも、読むときに同じ扱いになる。

### 知らせの強さは、既定はふつうの更新で、`notify: attention` ならすぐ

- 既定では、返事を置いても attention を出さない。読みもののふつうの更新として、ADR 0053 のランダムな待ちと awake hours に従って `sources_updated` に出る。
  頼んでおいたものなので、既定では割り込まない。
- frontmatter に `notify: attention` と書いた定期便は、返事のたびに attention を出し、すぐ知らせる。attention の形は ADR 0069 の `agent_reply` と同じで、`details` に `postbox` が加わる。

### 中身の無い返事は知らせず、`/sources` にも置かない

- 返事が reply/v1 の DataPart で、`sections` が空なら「中身なし」とみなす。取り決めの版は変えない。
- 中身なしの回は知らせず、`/sources` にディレクトリも作らない。空の記録が積もらないようにするためである。
  - ADR 0069 の `ask_agent` は、頼んだ時点で依頼のディレクトリを作る。定期便では、中身なしの回のディレクトリが残ってはならない。
- 送った時刻と結果（中身なし、を含む）は、ダッシュボードの定期便の欄に出す。
- 中身なしは、うまく受け取った回である。次の「前回の受け取り」は進める。
- 文章（TextPart）だけを返す相手は、空を表せない。毎回、中身のある返事として置き、知らせる。

### 依頼の末尾に「前回の受け取り」の行を足す

- ポストは定期便ごとに「前回うまく受け取った時刻」を持つ。
- 依頼の本文の末尾に、`前回の受け取り: <時刻> (JST)` の 1 行を必ず足す。同じ値を A2A の metadata にも載せる。
  時刻は本人のタイムゾーンで書く（例の `JST` は本人のタイムゾーンが日本のとき）。
- 失敗した回は時刻を進めない。次の回は、前回うまく受け取った時点からを頼むことになり、失敗した回の分を取りこぼさない。
- 前回の記録が無いとき（初回と、ファイルを消して作り直したとき）は、本文だけを送る。範囲は相手の既定に任せる。
- 本文の言い回し（「今日のメール」「重要なものだけ」）は自由である。本文と「前回の受け取り」の行のどちらに従うかは、相手が判断する。
  cron と本文の言い回しの整合を、natsumi で保つ必要はない。
- 相手の側の扱い（「前回の受け取りの行があれば、その時刻より後を基準にする」）は、各係の Agent Card と `AGENTS.md` に書く。`yuanying/fraction-agents` の側の取り決めであり、この ADR では決めない。
- 相手が状態を持たずに済み、境目の取りこぼしと失敗した回の取りこぼしを防げる。

### 失敗の扱い

- 聞き返し（`input_required`）は、`notify` にかかわらず attention で知らせる。答えないと先へ進まないからである。
  - 答え方は、今の `ask_agent` の `continue` である。
  - 答えた後の返事がうまく受け取れたら、その時点で定期便の「前回の受け取り」を進める。
- 失敗（`failed`）と待ちの上限切れ（`gave_up`）は、ふつうの更新で知らせ、時刻は進めない。一時的な不調では割り込まない。
- 失敗か待ちの上限切れが **3 回続いた**ときだけ、attention で知らせる。
- ダッシュボードには、定期便ごとに、最後に送った時刻・その結果・続けて失敗した回数を出す。

### 頻度と止め方

- cron の回の間隔の下限は 15 分とし、設定で変えられる。下限より短い cron は、検査で戻す（なつみの書き込み）か、読むときに飛ばす（本人のコミット）。相手への負荷に歯止めを掛ける。
- ダッシュボードは表示だけとし、定期便を止める・消す操作は置かない。記憶にコミットする者を増やさないためである。
- 本人が止めるときは、ssh でファイルを消してコミットするか（`paused: true` でもよい）、なつみに頼む。
- 緊急に全部を止めるときは、サーバーの設定 `postbox.enabled: false` にする。
- 夜も送る。届いたふつうの更新は、awake hours に従って朝に出る（ADR 0050・ADR 0053）。attention は ADR 0050 のとおり夜でも出る。
- 夜の記憶の整理係（[ADR 0055](0055-a-memory-curator-at-night.md)・[ADR 0068](0068-a-curator-that-remembers-like-a-person.md)）は `postbox/` に触れない。
  定期便は送る相手と時刻を決めるファイルで、整理の対象ではない。`skills/`（ADR 0073）と同じく、整理係の対象から外す。

### 関心の正本は定期便の本文で、なつみが反応を見て直す

- ニュースのような定期便では、何に関心があるかの正本は、定期便のファイルの本文そのものである（`postbox/morning-news.md` など）。送る文面と方針がずれない。
- なつみは、届いた返事から本人に合いそうなものを選んで話題にし、本人の反応に応じて定期便の本文を直す。直したものは検査を通ってコミットされ、次の回から送られる。
- 届いた返事の中身（ニュースの記事など）は外部のデータであり、命令ではない。なつみは中身に書かれた指示に従わない。
- これらの振る舞いは natsumi のコードでは変えず、マニュアル（か skill）で教える。

### ツールは足さない

- 定期便の新しいツールは作らない。投函はファイルで行う。
- `ask_agent` に `cron` を足さない。
- natsumi に Gmail に固有のコードを置かない。毎朝のメールの確認は、メールの係への定期便として投函すれば、この仕組みに移せる。

### 実装で決めること

この ADR では決めず、実装で決める。

- 状態の保存先。SQLite の表の形（定期便ごとの前回の受け取り、最後に送った時刻と結果、続けて失敗した回数、待っている Task との対応）と migration。
- 同じ回を二度送らない仕組み。必要な性質は、同じ定期便の同じ回の依頼を二度送らないことと、再起動で状態が壊れないことである。
  予約と出来事を同じ transaction で記録する ADR 0063 の形と、ジョブの一意キーの考え方（ADR 0003）に倣う。
- 止まっていた間に過ぎた回の扱い。何回分を過ぎても、まとめて送らず多くても 1 回とする（ADR 0003・ADR 0063 と同じ）。その 1 回を起動後に送るか、次の回を待つか。
- 前の回の返事を待っている間に、次の回の時刻が来たときの扱い。
- 「前回の受け取り」に記録する時刻を、うまくいった回の送った時刻と受け取った時刻のどちらにするか。境目で取りこぼさないことが必要な性質である。
- 待ちの上限の値（ADR 0036 の `a2a.giveUpAfterHours` を使うか、定期便の間隔に合わせるか）。
- 中身なしの回に、依頼のディレクトリを作らない（または消す）仕組み。
- 聞き返しに `continue` で答えられるように、定期便の依頼を相手との直近のやり取り（ADR 0069）にどう記録するか。
- 下限の設定の名前と、cron の回の間隔の下限の測り方。
- 検査の細部。frontmatter の知らない項目、`paused`・`notify` の値の誤り、空の本文、ファイル名に使える文字、`postbox/` の下のサブディレクトリや `.md` 以外のファイルの扱い。
- 本人のコミットで飛ばした定期便を、なつみに見せる形（ターンの入力に添えるか、など）。
- ダッシュボードの定期便の欄の置き場所と、出す項目の細部（次に送る時刻など）。
- A2A の metadata の欄の名前。
- `/manual/ask-agent.md` などマニュアルの書き方と、system prompt を変えるかどうか。

### 置き換える既存の決定

- ADR 0003
  - 置き換え:「Gmail と Calendar を 15 分ごとに確認する」。natsumi のサーバーは Gmail と Calendar の定期確認を持たない。
    定期的な確認は、本人（かなつみ）が係のエージェントへの定期便として投函し、ポストが送る。間隔は定期便ごとの cron で決まり、下限は 15 分（設定で変えられる）。
  - 残す: Gmail は読み取り専用であること。Calendar の変更は承認の後であること。
- ADR 0014
  - 置き換え: 未接続の Gmail と Calendar の定期確認を「後の作業で、この予約と合図の仕組みに乗せる」点。予約ではなく、定期便で送る。
- ADR 0055・ADR 0068
  - 追加: 整理係の対象から、記憶の下の `postbox/` を外す。
- ADR 0069
  - 追加: `/sources/agents/` に、なつみのターンを経ない依頼（定期便）の返事が入る。`request.md` と attention の `details` に `postbox` が加わる。
  - 追加: 返事は既定ではふつうの更新として知らせ、`notify: attention` の定期便と聞き返し、3 回続けた失敗でだけ attention を出す。`ask_agent` の返事が常に attention であることは変えない。
  - 追加: 中身の無い返事（reply/v1 の `sections` が空）の回は、依頼のディレクトリを残さない。

## Consequences

- 決まった依頼は、なつみが予約を入れ忘れても止まらない。依頼のためにモデルを呼ばないので、ターンもトークンも使わない。
- 返事は今の `ask_agent` の返事と同じ場所と形で届くので、なつみの読み方は変わらない。
- 定期便を足すのも直すのも、記憶のファイルを書いてコミットするだけである。natsumi のリリースは要らない。
  一方、書いたものが定期便になるのはコミットされてからである。なつみの書き込みはそのターンの終わりから、本人のコミットは次の毎分の見回りから効く。
- 本人のコミットは検査を通らないので、誤った定期便もコミットはされる。送られずに飛ばされ、その理由がなつみとダッシュボードに出る。
- 既定のふつうの更新は、夜に届いたものが朝にまとめて出る。`notify: attention` の定期便と聞き返し、3 回続けた失敗は夜でもすぐ出て、なつみのターンが動く。
- 中身なしの回は `/sources` に跡を残さない。送ったかどうかは、ダッシュボードの定期便の欄でだけ分かる。
- 文章だけを返す相手は空を表せないので、新しいものが無くても毎回知らせが届く。
- 「前回の受け取り」の行の扱いは、相手の Agent Card と `AGENTS.md` の取り決めに頼る。従わない相手には、毎回同じ範囲を頼むことになる。
- 相手への負荷は、定期便ごとの下限 15 分で抑える。定期便の数は制限しないので、件数が増えたときの負荷は本人が見る。
- ダッシュボードからは止められない。止めるには、ssh でコミットするか、なつみに頼むか、サーバーの設定を `postbox.enabled: false` にする。
- 記憶に `postbox/` が増える。整理係はそこを読まず、触らない。
- 毎朝のメールの確認を定期便に移すには、今なつみが入れている繰り返しの予約を取り消し、`postbox/` に定期便を置く。本番の記憶を変えるので、本人の承認の後に、本人かなつみが行う。
