# 0039. Slack は読むファイルとして受け取り、ポッポさんは問題点ごとの点数で判定する

- Date: 2026-09-25
- Status: Accepted（「ADR 0012 のまま進めるもの」のうち「本文のある投稿は、判定が『送る』でも最初はすべて本人の承認を待つ」は [ADR 0040](0040-the-dove-sends-what-the-judge-passes.md) で置き換え、アイコンの置き場所と渡し方は同 ADR で決定、判定のモデルを Jev に限る点は同 ADR で置き換え（Jev の API と OpenAI 互換のモデルの logprobs の 2 つの方式、既定は後者）、リアクションの絵文字を候補の一覧に限る点は [ADR 0042](0042-any-emoji-that-exists.md) で置き換え、チャンネルのファイルへのリアクションの記録と `updates` の `reactions_on_mine` は [ADR 0043](0043-reactions-in-the-channel-files.md) で追加、後日の範囲としていた画像の投稿は [ADR 0044](0044-drawing-with-sdctl-and-posting-images.md) で決定（画像の中身を検査しない点は残し、前提の「意図しない画像を作れない」は同 ADR で崩れる）、「イベントの種類は増やさず、更新元を足す」・合図の `updates` の欄・`slack_mention` のイベント・チャンネルのファイルを Markdown で書く点は [ADR 0050](0050-telling-of-source-updates-with-one-event.md) で置き換え（更新は `sources_updated` の 1 種類で知らせ、メンションと DM はその `attention`、ファイルは JSON Lines）、問題点の並びは [ADR 0059](0059-two-judges-side-by-side-and-fewer-issues.md) で置き換え（スレッドに無い情報をやめ、本人に代わる約束と私的な事情の問いを変える）、ポッポさんへの依頼の見出し付きのテキスト（`返信先`・`種類`・`表情`）と返信先の参照の文字列は [ADR 0074](0074-asking-poppo-in-json-and-hearing-back-in-sources.md) で置き換え（JSON の欄と、`to` の `{file, path}`））

## Context

[ADR 0012](0012-slack-and-colleagues.md) で、Slack 連携の骨組みを決めた。
natsumi 専用の bot を Socket Mode でつなぎ、Slack のイベントは思考ループのイベントとして渡す。
natsumi は Slack に投稿するツールを持たず、投稿は送信役の同僚「ポッポさん」への依頼だけで行う。
ポッポさんが判定し、本文のある投稿は本人の承認を待つ。

実装に入る前に、次の点が決まっていなかった。

- 招待したチャンネルの発言を、どこまで思考ループの割り込みにするか。
  発言のたびにイベントにすると、雑談のたびに思考ループが動き、本人のメッセージが待たされる。
- 読めるチャンネルの中身を、natsumi がどう読むか。専用のツールを足すと、ツールの説明の分だけ context を使い、
  prefix cache も壊れる（[ADR 0019](0019-a-workspace-not-a-memory-tool.md)、[ADR 0036](0036-a-manual-to-read-and-a-limit-on-waiting.md)）。
- 定期の合図（`ping`・`self_check`、[ADR 0014](0014-self-checks-and-pings.md)）のときに、何が新しく来たかをどう知らせるか。
  Slack の後にも、確かめたい更新元は増える見込みである。
  そこで「イベントの種類を外から自由に増減できるようにするか」が問いになった。
- ポッポさんに何をどの形で頼むか、返信先をどう指すか。Slack の発言の ID（ts）は形の似た文字列であり、
  モデルに写させると間違える（[ADR 0024](0024-no-event-ids-for-the-model.md)）。
- 複数のワークスペースの、複数のチャンネルに参加させること。
- 画像を受け取ること。natsumi のモデルは画像を読める。
- ポッポさんの判定に使うモデル。

ADR 0012 は判定のモデルにサブスクリプション経路の GPT を当て、判定と短い理由を決まった形で出させるとしていた。
本人はこれを、TypeSafe AI の Jev に替えると決めた。Jev は判定のためのクラウドの API で、従量課金である。
問いの型は、選択肢から選ばせる Choice（確率と確信度を返す）、点数を返す Score、真偽を 0〜1 で返す Noul がある。
自由な文章は返さず、画像も見られない。ローカルで動かす手段の案内は無い。データの保持と日本語の扱いは確かめていない。

ADR 0012 の「決まった文面の一次回答（例:「確認して、このスレッドで返します」）は自動」は、
評価で同じ「確認中です」の類の投稿を繰り返す形になった。

現時点で natsumi を参加させるのは、中身が外に漏れても困らないチャンネルだけである。
本人は、これをテストの段階と位置づけている。

## Decision

### なつみの側の約束は 3 本

外から来るものと外へ出すものを、次の 3 本に分ける。

| 約束 | 何が乗るか |
| --- | --- |
| 割り込みはイベント | 本人のメッセージ、Slack のメンションと DM、エージェントの返事 |
| 読むものはファイル | 作業環境の `/sources/<更新元>/` にある読み取り専用のファイル |
| 外に作用する頼みは `ask_agent` | Slack への投稿とリアクション（ポッポさんへの依頼）、ほかのエージェントへの依頼 |

- Slack の割り込み（イベント）は、bot への本物のメンションと DM だけとする。
  - 名前が出ただけの発言や、チャンネルの流れの発言はイベントにしない。ファイルに書き、合図のときに件数で知らせる。
  - 反応するかどうかは、合図のときに natsumi が決める。メンション以外の発言にも返せる（後述の参照の形）。
- 読むための専用のツールは足さない。natsumi は `run_shell` でファイルを読む。

### 更新元の枠

- 読むものはすべて、更新元ごとに `/sources/<更新元>/` の下の読み取り専用のファイルと、その目次の `INDEX.md` で見せる。
  - 全部を書くと重いものは、中身ではなく参照先のリンクなどをファイルに書く。
- 合図のイベント（`ping`・`self_check`）に `updates` の欄を足し、更新元ごとに「前回この欄を見せてから増えた件数」と見るべきファイルを載せる。
  - 何も増えていなければ、欄ごと付けない。
  - 見せたことを記録し、次の合図の件数は、そこから数える。
- 更新元の実装はサーバーのコードで持ち、有効・無効は設定で切り替える。思考ループは更新元がいくつあるかを知らない。
- 最初の更新元は Slack である。
- 「イベントの種類を外から増減できるようにするか」への答えは、これである。イベントの種類は増やさず、更新元を足す。
  - 更新元を足しても、system prompt とツールの定義は変わらない。読み方はマニュアル（ADR 0036）に 1 枚足す。

### Slack のチャンネルのファイル

- サーバーは、bot を招待したチャンネルの発言を、`/sources/slack/` の下にワークスペース・チャンネル・日付で分けた Markdown に書く。
  - 発言の見出しは、なつみのタイムゾーンの時刻を秒まで書き、`## 14:32:05 山田` の形とする。
  - スレッドの返信は、親の発言の下に字下げして書く。
  - 発言が編集・削除されたら、その日のファイルを書き直す。
  - 画像は同じ場所に取ってきて、Markdown にはそのパスを書く。種類と大きさの上限を超えたものは、添付があったことだけを書く。
- `/sources/slack/INDEX.md` には、チャンネルごとの最後の更新の時刻を書く。
- 起動時と、Slack につなぎ直したときに、チャンネルごとの最後に記録した時刻から履歴を取り直して埋める。
- ファイルは消さない。古いものの掃除は本人が手で行う。

### メンションと DM のイベント

- イベントには、本文、発言者、ワークスペースとチャンネル、`返信先` にそのまま写せる参照（後述）、ファイルのパスを載せる。
- 流れも一緒に載せる。スレッドの中ならそのスレッドの直近の数件、チャンネル直下ならその前の数件である。件数と文字数の上限はサーバーが持つ。
- メンションや DM に付いた画像は、画像のまま添える。
- Slack の ts やイベントの ID は載せない（ADR 0024）。
- メンションか DM を受け取ったら、サーバーが自動で 👀 のリアクションを付ける。natsumi は関わらない。絵文字は設定で変えられる。

### 画像

- 受け取りは今回の範囲とする。メンションと DM の画像はイベントに添え、チャンネルの画像はファイルと一緒に置く。
- チャンネルの画像は、見たいときだけ shell で開く。作業環境に `view <パス>` のコマンドを用意し、その結果に画像そのものを載せる。ツールは増やさない。
  - 受け取った時点で画像を説明文にしておく形は、今は作らない。1 枚ごとのモデルの呼び出しが、思考ループとモデルを取り合うからである。
  - この形は、Pi のツールの結果に画像を載せられることを前提とする。載せられなければ、受け取り時に説明文を作る形に倒す。
- 画像の投稿は後日の範囲とする。
- 画像の中身は検査しない。本人の判断である。natsumi は画像を作る手段を持たない予定であり、Jev も画像を見られない。

### ワークスペースと App

- ワークスペースごとに Slack App を作る。bot token と Socket Mode の token の組を、ワークスペースの数だけ持つ。
- 設定はワークスペースの一覧に token の組を持つ形にする。後で 1 つの App を配布する形に移っても、設定の形がほぼ変わらないようにするためである。
- token は秘密として扱い、設定ファイルに値を書かない（ADR 0004 と同じ）。本人の user token は使わない（ADR 0012 のまま）。
- 参加するチャンネルは、bot の招待で決まる。

### ポッポさんへの依頼

- ポッポさんは `ask_agent` の相手の 1 人とし、頼める相手の一覧（`/manual/agents/INDEX.md`、ADR 0036）に載せる。Slack のためのツールは足さない。
- 依頼の `message` は見出し付きのテキストとする。サーバーが見出しを検査し、形が崩れていれば頼まずに突き返す。

| 見出し | 中身 |
| --- | --- |
| `返信先` | 返す相手の発言、または投稿するチャンネル |
| `種類` | 投稿かリアクションか |
| `表情` | Slack に出すアイコンの表情（後述） |
| `---` の後 | 本文。リアクションなら絵文字 |

- 返信先は、ファイルに書かれた発言を参照する形で書く。メンションへの返事に限らず、ファイルにある発言ならどれにも返せる。
  - 発言は `work/#dev 2026-09-25 14:32:05 山田` の形（ワークスペース・チャンネル・日付・秒までの時刻・発言者）で指す。
  - チャンネルそのものへの投稿は `work/#dev` と書く。
  - サーバーはファイルの記録と突き合わせる。一意に決まらなければ、候補の本文の書き出しを添えて突き返し、指定し直させる。
  - Slack の ts は写させない（ADR 0024）。

### 判定のモデルは Jev

- ポッポさんの判定は Jev で行う。すべてのワークスペースで使い、ワークスペースごとに使う・使わないの設定は作らない。
  - 送るデータがクラウドに出ることは、参加させるのが漏れてよいチャンネルだけであるというテストの段階の前提で受け入れる。
    この前提は、あるワークスペースの内容が別のワークスペースへの投稿に混ざる漏えいへの手当てにもなっている。
  - Jev は本人が選んだ従量課金の API である。ADR 0004 の「従量課金の API へ無断で切り替えない」には当たらない。
- 判定の材料は ADR 0012 のまま、下書きと、サーバーが取った返信先の周りの発言だけとする。natsumi の説明や記憶は見せない。
- 判定は、問題点ごとに Noul で聞く。「スレッドに無い情報」「本人に代わる約束・期限」「隠しごとの匂わせ」「事実と違う説明」「同意の捏造」などを並べて、一度に評価する。
  - しきい値を超えた問題点を、判定の理由とする。
  - 「送る・本人に回す・突き返す」は、点数からサーバーの決まりで出す。しきい値は設定で持つ。
  - natsumi への返事の台詞と、承認画面の理由は、サーバーが点数から整える。
- 返信をスレッドに入れるかチャンネルに出すかも、同じ呼び出しの別の問いとして Choice で Jev に選ばせる。
  natsumi は返す相手の発言を指すだけで、置き場所は決めない。チャンネルの流れに沿った会話なら、無理にスレッドに返さなくてよいからである。
- Jev が使えないか答えが崩れたときは、ADR 0012 のとおり「判定なし」として本人の承認に回す。
  置き場所は、サーバーの決まり（指した発言がチャンネル直下で、その後の発言が一定の件数以内ならチャンネル、ほかはスレッド）で初期値を決め、本人が承認画面で直せる。
- 本人の判断との一致は、問題点ごとと、置き場所の判定について記録する。承認画面には問題点ごとの点数を並べる。

### リアクション

- natsumi は、ポッポさんへの依頼（`種類` にリアクション、本文に絵文字）でリアクションを付けられる。
- 絵文字はサーバーの持つ候補の一覧に限る。本文を書かないので、Jev の判定も本人の承認も通さない。
- 決まった文面の一次回答は作らない。受け取った合図は、自動の 👀 で出す。

### 本人の承認

- 承認は iPhone のアプリで行う。承認待ちができたら push 通知を送り（[ADR 0029](0029-push-notifications-on-the-iphone.md)）、アプリで承認・修正・却下を選ぶ。
- Mac には、後で同じ画面を足す。

### 返事のアイコン

- Slack への返事のアイコンを、なつみの表情に合わせて投稿ごとに変える。
- 表情は、ポッポさんへの依頼の `表情` の見出しで渡す。値は [ADR 0026](0026-a-feeling-on-each-line.md) の表情と同じ一覧とする。
- アイコンの画像の置き場所と、Slack に渡す方法の細部は、送信の作業単位の前に決める。

### ADR 0012 のまま進めるもの

- 同じ返信先の書き直しは 2 回までとし、3 回目の突き返しは下書きと理由の履歴を添えて本人に回す。
- 本文のある投稿は、判定が「送る」でも最初はすべて本人の承認を待つ。承認は送る本文と返信先の全体に結び付ける。
- 送る直前の機械的な検査、同意の証拠はサーバーの承認記録だけ、という点も変えない。

### 置き換える既存の決定

- ADR 0012
  - 置き換え:「自動で出すのは、リアクションと、決まった文面の一次回答」。一次回答は作らない。自動で出すのは、受け取ったときの 👀 と、natsumi が依頼した候補の中のリアクションである。
  - 置き換え:「入力を小さく絞れる重要な判定（ポッポさん）は、サブスクリプション経路の GPT を使う」。判定は Jev で行う。
  - 置き換え:「判定は『送る』『本人に回す』『突き返す』のどれかと、短い理由の決まった形で出させる」。問題点ごとの Noul の点数を聞き、判定と理由はサーバーが点数から出す。
  - 具体化:「読めるのは、bot を招待したチャンネルと、bot へのメンションだけ」。割り込みはメンションと DM、チャンネルの中身は `/sources/slack/` のファイル。
  - 具体化:「natsumi が渡すのは、下書きと返信先のスレッドの指定だけ」。`ask_agent` の見出し付きテキストで渡し、返信先はファイルの発言の参照で書く。スレッドかチャンネルかは Jev が選ぶ。
  - 具体化:「natsumi 専用の Slack App」。ワークスペースごとに App を作る。
  - 決定: 範囲外としていた「名前が出ただけの雑談に反応するか」。イベントにはせず、合図の `updates` で知らせ、反応するかは natsumi が決める。
- ADR 0014
  - 追加: `ping` と `self_check` のイベントに `updates` の欄。
- ADR 0019・ADR 0036
  - 追加: 作業環境に見せる読み取り専用の場所として `/sources`。shell に `view` のコマンド。natsumi が書ける場所は変わらない。

## Consequences

- チャンネルの雑談では思考ループが動かないので、本人のメッセージが Slack で待たされることは減る。
  その代わり、メンション以外の発言への反応は、次の合図まで遅れる。
- 更新元を足しても、イベントの種類、system prompt、ツールの定義は変わらない。更新元ごとにサーバーのコードと、マニュアルの 1 枚が増える。
- チャンネルのファイルを消さないので、data directory は増え続ける。掃除は本人の手作業に頼る。個人データとしてバックアップの対象になる。
- 返信先の参照は秒までの時刻と発言者で決まるので、同じ秒の同じ人の発言は一意にならず、突き返しと指定し直しが要る。
- 下書きと周りの発言がクラウドの Jev に送られる。漏れてよいチャンネルだけに参加させるという前提が崩れたら、ワークスペースごとに使う・使わないを選べる設定を足すなど、この決定を見直す。
  Jev の料金は判定の回数に比例してかかる。Jev が止まれば、判定なしの件が本人の承認に回る。
- Jev は自由な文章を返さないので、判定の理由は、事前に並べた問題点の中からしか出ない。並べていない種類の問題は、点数に表れない。
- 判定の理由が問題点の名前として残るので、本人の判断との一致を問題点ごとに比べられる。自動で送る範囲を広げる判断（ADR 0012）の材料が細かくなる。
- 決まった文面の一次回答が無いので、本文の返事は本人の承認まで届かない。その間に相手に見えるのは 👀 だけである。
- 承認は iPhone でしかできない。Mac の承認画面ができるまで、iPhone が手元に無いと投稿は止まる。
- 画像の中身を検査しないので、画像の投稿を足すときには、その前提（natsumi が画像を作れない）を確かめ直す。
- `view` が Pi のツールの結果に画像を載せられなければ、受け取り時に説明文を作る形に変え、思考ループとモデルを取り合う分の負荷を受け入れる。

実装は次の順で進める。

1. 受け取り側: 接続、チャンネルのファイルと埋め直し、メンションと DM のイベント、自動の 👀、`updates` の枠と `/sources/`、shell の `view`
2. ポッポさんと送信: `ask_agent` での依頼と見出しの検査、Jev の判定、書き直しの回数、承認の記録と API、機械的な検査、送信、リアクション、返事のアイコン
3. iPhone の承認画面と push 通知
4. 画像の投稿（後日）
