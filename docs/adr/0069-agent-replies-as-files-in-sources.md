# 0069. 外のエージェントの返事は /sources にファイルで置き、sources_updated で知らせる

- Date: 2026-10-05
- Status: Accepted

## Context

外のエージェントへの依頼（`ask_agent`）の返事は、[ADR 0035](0035-asking-outside-agents-and-hearing-back.md) の形で届いている。
サーバーが待っている Task を定期的に取りに行き（ポーリング）、済む・聞き返す・失敗する・待ちの上限を過ぎる（[ADR 0036](0036-a-manual-to-read-and-a-limit-on-waiting.md)）と、
`agent_reply` の出来事を思考ループのキューに入れる。出来事には返事の本文がまるごと入る。

本人の困りごとは、長い返事（調べものの結果など）で文脈が膨らむことである。
本文は出来事としてそのまま Pi の session に入り、ターンが終わっても、畳み込み（[ADR 0047](0047-folding-ended-turns-with-a-memo.md)）までは残り続ける。
本人は、要約だけを読み、マスターの問い次第で詳細を見る形にしたいと考えた。

手元には次のものがあった。

- 相手が返した画像は、すでに「ファイルに置き、出来事にはパスと説明だけを載せる」形である（[ADR 0048](0048-bringing-in-images-an-agent-hands-back.md)）。文章も同じ扱いに揃えられる。
- 読みもの（Slack のチャンネルなど）は、サーバーが `/sources` の下にファイルとして置き、`sources_updated` の 1 種類の出来事で知らせている（[ADR 0050](0050-telling-of-source-updates-with-one-event.md)）。
  出来事には、変わったディレクトリ・なつみ宛ての印（`attention`）・差分の見方だけを載せ、本文は載せない。`attention` は間隔を待たずにすぐ出る。
  `/sources` はサーバーだけが書き、作業環境からは読み取り専用である。
- Codemode（[ADR 0066](0066-codemode-to-keep-raw-output-out-of-the-context.md)）を使えば生の出力を文脈に入れずに済むが、本番では off である。
  Codemode が無くても、要約だけを読み、必要な節だけを後から読めなければならない。

返事の受け取り方（ポーリング・SSE・webhook）も相談したが、どれを選んでも、文脈に入る量は変わらない。
受け取り方は今のポーリングのままとする。

A2A の DataPart は中身のスキーマを決めていない。相手が構造のある返事を返すには、natsumi と相手の間の取り決めが要る。
最初に取り決めを結ぶ相手は、`yuanying/fraction-agents` の調べもの係である。

細部は本人との問答で決めた。途中で本人から「`agent_reply` をやめて `sources_updated` でよいのではないか」という方向の変更があり、
返事の置き場は `/work/agents/` から `/sources/agents/` に移った。

## Decision

### 方針: 外から届くものは、可能な限り `sources_updated` に寄せる

- なつみのアーキテクチャの方針として、外から届くもの（外のエージェントの返事など）は、可能な限り `sources_updated` で知らせる。
  - 中身は、サーバーが `/sources` の下にファイルとして置く。
  - 出来事には、場所と印（`attention`）と短い要約だけを載せる。本文は載せない。
- 外から届くものに専用の出来事を新しく作る前に、まずこの形で足りないかを考える。
- 理由は次のとおりである。
  - 出来事の大きさが、届いたものの大きさに引きずられない。なつみは要約で足りなければ、必要な分だけをファイルから読む。
  - 出来事の種類が増えない。system prompt の出来事の説明も増えない（[ADR 0019](0019-a-workspace-not-a-memory-tool.md) の prefix の制約）。
  - 届いたものが `/sources` に残り、`sources-diff` と同じ道具で後から探せる。
- 最初の適用が、この ADR の外のエージェントの返事である。

### DataPart の中身は、すべての相手に共通の形 1 つ

- 返事の DataPart の中身は、相手によらず次の 3 つからなる。

| 欄 | 中身 |
| --- | --- |
| `summary` | 3 行以内の要約 |
| `sections` | 節の並び。各節は `title` と Markdown の `body` |
| `sources` | 出典の並び。各出典は `title` と `url` |

- 相手に固有のものは、節の中に書く。natsumi 側の置き方と読み方が 1 つで済み、相手を増やしても変わらない。
- 退けた案:
  - 共通の土台に、相手ごとの追加の欄を足す。取り決めが相手の数だけ増える。
  - 相手ごとに別の形にする。natsumi に相手ごとの処理が要る。

### 返事 1 件を 1 つのディレクトリに、節を 1 ファイルずつ置く

- サーバーは返事ごとにディレクトリを作り、`/sources/agents/<相手の名前>/<日時>-<短い印>/` に置く。日時は UTC の `20261005T013000Z` の形である。
- ディレクトリの中身は次のとおりである。

| ファイル | 中身 |
| --- | --- |
| `README.md` | 要約、節の一覧（パスと字数）、出典の数 |
| `01-<節の題>.md`、`02-<節の題>.md` … | 節の本文。1 節 1 ファイル |
| `sources.json` | 出典の並び |
| `result.json` | サーバーの記録: どちらの形で置いたか、置いた返事、受け取った DataPart そのまま（作業単位 4 で決めた） |
| `images/` | 相手が返した画像（次の節） |

- なつみは `read` で節を 1 つ丸ごと読める。要約で足りなければ `README.md` を読み、必要な節だけを読む。Codemode は要らない。
- 退けた案:
  - Markdown 1 つと行番号の一覧。行番号を写し間違えやすい。
  - JSON だけ。Codemode や jq が無いと本文が読みにくい。

### 知らせは `sources_updated` の `attention` で、`agent_reply` の出来事はなくす

- 返事を置いたら、サーバーは `agents` の更新元として `attention` を出す。`attention` は間隔を待たずにすぐ出る（ADR 0050）。
- `attention` に載せるのは、種類 `agent_reply`・相手の名前（`agent`）・状態（`state`）・返事のディレクトリの場所・要約（`summary`、3 行以内）である。
  - 要約で足りれば、なつみは何も読まずに答えられる。節の一覧は `README.md` を読む。
  - 退けた案: 場所だけ（毎回 1 回読むことになる）、要約と節の一覧まで（節が多いと長くなる）。
- 完了以外の状態も、同じ形で知らせる。
  - どの状態の返事も同じディレクトリの形で置き、`state` を `completed`・`input_required`・`failed`・`gave_up`（待ちの上限切れ）のどれかにする。
  - 聞き返しの質問や失敗の理由は短いので、`summary` に入れる。
  - 聞き返しに答えるのは、今どおり `ask_agent` の `continue` である。
  - 退けた案: 完了以外は今の `agent_reply` の出来事のまま残す。出来事が 2 種類残る。
- 外のエージェントの返事の `agent_reply` の出来事は、完全になくなる。

### 相手が返した画像も `/sources` の返事のディレクトリに置く

- 相手が返した画像は、返事のディレクトリの `images/` に置く。返事が 1 か所にまとまる。
- 取り込みの規則（同じ origin だけ、大きさ、枚数、形式、名前の付け方）は ADR 0048 のままとする。
- 検査と写しは、今の部品（[ADR 0044](0044-drawing-with-sdctl-and-posting-images.md)・[ADR 0045](0045-showing-the-owner-images-with-a-reply.md)）を使う。
- `reply_to_mac` の `images` には、`/work` の下に加えて `/sources/agents/` の下のパスも並べられるようにする。
- 退けた案:
  - 画像は `/work` に残す。返事が 2 か所に分かれる。
  - 両方に置き、なつみが `cp` する。手順が増える。

### DataPart に対応していない相手の返事は、サーバーが同じ形に作る

- 文章（TextPart）だけの返事は、サーバーが Markdown の見出しで節に切り、先頭の段落を要約にして、同じディレクトリの形で置く。
- なつみからは、相手が DataPart に対応しているかどうかは見えない。他人のエージェントもそのまま使える。
- 退けた案:
  - 本文を 1 ファイルに置く。全部読みやすいが、要約だけを読む形にならない。
  - DataPart を必須にする。他人のエージェントが使えない。

### DataPart の形の取り決めは、拡張の URI と JSON Schema で結ぶ

- `yuanying/fraction-agents` に、取り決めの文書と JSON Schema を置く。版を含む拡張の URI（例: `…/reply/v1`）を、相手の Agent Card に書く。
- natsumi は、その拡張を名乗る相手にだけ DataPart を求める。受け取ったら JSON Schema で検証し、合わなければ文章の返事の扱い（前の節）に戻る。
- 退けた案: 文書だけで結ぶ。相手が対応しているかを、返事を見て判断するしかない。

### 返事は消さない

- 返事のディレクトリは、Slack の記録と同じく残す。後で「前に調べたこと」を探せるようにする。
- 画像の量が問題になったら、そのときに決める。
- 退けた案: 一定の日数で消す（古い調べものを探しにくい）、画像だけ消す。

### 進め方

1. この ADR。
2. natsumi: 返事を `/sources/agents/` に置き `attention` で知らせる、文章の返事を節に切る、`agent_reply` をなくす、画像も `/sources` に置く、`reply_to_mac` の `images` に `/sources/agents/` を加える。
3. `yuanying/fraction-agents`: 拡張の URI、JSON Schema、調べもの係が DataPart を返す。
4. natsumi: 拡張を名乗る相手に DataPart を求め、検証する。

- 2 だけで、文脈の膨らみは止まる。2 と 3 は並行できる。

### 実装の PR で決めること

- `ask_agent` の結果の文とツールの説明。「返事は `sources_updated` の `attention` で届く」の類にする。ツールの説明は固定の文のまま変える（ADR 0019）。
- system prompt の出来事の説明と、`/manual/ask-agent.md` の書き換え。`agents` の更新元のマニュアルを足すかどうか。
- `attention` の欄の形。今の `attention` は `file`・`path`（`jq -s` のパス）・`kind` を持ち、相手の名前・状態・要約の欄を持たない。返事のディレクトリの場所と、新しい欄をどう載せるか。
- `agents` の更新元の登録（活発さを測るディレクトリの深さ、差分から外すファイル）と、初めて見るディレクトリの扱い（ADR 0050 は黙って ref を置く）で最初の返事が落ちないこと。
- `sources-diff` で返事がどう見えるか。
- `agent_replies` の表と、移行の時点で返事を待っている Task の扱い。
- 節のファイル名の作り方（題の文字の扱い、長さ、重なったとき）と、ディレクトリ名の短い印の作り方。Task や context の ID は使わない（[ADR 0024](0024-no-event-ids-for-the-model.md)）。
- 要約の長さの上限と、上限を超えたときの扱い。文章の返事を節に切る細部（見出しが無いとき、先頭の段落が長いとき）。

実装（作業単位 2）で、上の各項を次のとおり決めた。

- ツールの結果の文と説明
  - `ask_agent` の結果は、依頼を置いたディレクトリの場所と「返事は後で同じディレクトリに置かれ、`sources_updated` の attention（kind: agent_reply）として届く」ことを言う（次の「依頼もディレクトリに置く」）。前の返事を待っている間の `continue` の断りも、attention で届いてから続けるように言う。
  - ツールの説明は固定の文のまま書き換えた。依頼ごとのディレクトリと `request.md`、attention の欄（agent・state・summary・request・asked_at・file）、state の 4 つ、要約で足りなければ `README.md` と要る節だけを読むこと、`/manual/ask-agent.md` の場所を書く。
  - ポッポさんの結果だけは `agent_reply` の出来事で届くことも、説明に書く。ポッポさんへの依頼も同じ `ask_agent` を通るからである。
  - `reply_to_mac` の説明に、`/sources/agents` の下の画像も並べられることを足した。
- system prompt とマニュアル
  - system prompt の `sources_updated` の説明を、Slack と外のエージェントの返事の両方に合うように直した。`path` はあるときだけの欄とし、`agent_reply` の読み方は `/manual/ask-agent.md` にあると書く。
  - `agents` の更新元のマニュアルは足さない。頼み方と返事の読み方は 1 つのページで続けて読むものなので、`/manual/ask-agent.md` に返事のディレクトリと読み方を書いた。
- `attention` の欄の形
  - 更新元が自分の欄を持てるようにした（`details`、migration 26）。出来事では `source`・`kind`・`file` の横に並び、これらを上書きしない。
  - 外のエージェントの返事では、`file` を依頼のディレクトリの `README.md` にし、欄は `agent`・`state`・`summary`、頼んだ文面の先頭の行（`request`、80 字まで）、頼んだ時刻（`asked_at`、本人のタイムゾーン）と、画像があるときだけ枚数の `images` とする。この版より前の依頼の返事には、`request` と `asked_at` が付かない。
  - ディレクトリの場所は `file` と、出来事の `changed` の `dir` で分かる。ADR の「`path`（返事のディレクトリ）」は、`jq -s` のパスの `path` と名前がぶつかるので使わない。`path` は省けるようにした。
  - 返事の画像は attention の画像として出来事に添えない。添えると画像が文脈に入るからである。`README.md` に並べ、なつみが要るときに `view` で見る。
- `agents` の更新元の登録と、初めて見るディレクトリ
  - 依頼ごとに測る（深さ 2、`agents/<相手>/<依頼>`）。返事は依頼と同じディレクトリに入る。
  - 依頼のディレクトリは、初めて見るディレクトリとして ADR 0050 のとおり黙って ref が置かれる。依頼を置いたことは知らせない。
  - 返事が入ると、そのディレクトリは変わったものとして出来事に出る。返事より先に取り込まれていなければ、初めて見るディレクトリとして黙って取り込まれる。どちらでも attention はデータベースで待つので落ちず、attention のあるディレクトリは差分が無くても出来事に出る。
  - attention は、待っている Task の状態の更新と同じトランザクションで記録し、コミットしてから出来事を求める。依頼のディレクトリは、git が無視する名前（`.tmp`）で作ってから置き場所に移す。返事は、前の試みが残したものを消してから書き、`README.md` を最後に書く。書けなかったときは `request.md` だけを残す。
  - Slack が無くても、`a2a` があれば `sources` を用意する。用意できないときは返事を受け取れないので、`ask_agent` は頼まずに断る。
- `sources-diff` での見え方
  - 履歴に入れるのは `request.md` と `README.md` だけとする。節のファイル・`result.json`・`sources.json`・`images/` は外す。`sources-diff` には頼んだことと返事の要約と節の一覧が出て、返事の本文が大きく出ることはない。
  - 前に頼んだことと受け取った返事は、`/sources/agents/<相手>/` を `ls` や `grep -r` で探す。
- `agent_replies` の表と移行
  - 新しい行は作らない。表と `agent_reply` の出来事の型は残す（ポッポさんが使う）。
  - 版を上げた時点でまだなつみに渡していない A2A の `agent_reply` の出来事は、前の形のまま 1 度だけ渡す。待っている Task は `agent_tasks` に残っているので、新しい版で取りに行き、`/sources/agents/` に置く。どちらも取りこぼさない。
  - 待っている古い Task には依頼の場所が無いので、届いたときに返事のためのディレクトリを作る（名前の日時は受け取った時刻）。`README.md` の「頼んだこと」には、記録が無いと書く。
- 節のファイル名とディレクトリ名
  - 節のファイル名は、01 からの番号と題である。題は NFKC で正規化し、文字と数字以外を `-` にまとめ、40 字で切る。何も残らなければ `section` とする。番号があるので、同じ題が重なってもぶつからない。
  - ディレクトリ名は、頼んだ時刻（UTC）とランダムな 16 進 4 桁の短い印である。同じ名前があれば引き直す。Task や context の ID は使わない。
  - 画像のファイル名は、相手の付けた名前を安全な形にしたものである（日時は付けない。ディレクトリ名にあるため）。重なれば `-2` などを付ける。
- 要約の長さと、文章の返事の切り方
  - 要約は 3 行・300 字までとする。超えた分は切り、末尾に「…」を付ける。全文は節のファイルに残る。
  - 節は、2 回以上現れる見出しのうちいちばん上の段で切る。どれも 1 回なら、いちばん上の段で切る。大見出し 1 つの下に節が並ぶ返事でも、節が 1 つにまとまらない。コードブロックの中の `#` は見出しにしない。
  - 最初の見出しより前の文は、それだけで 1 節にする。前に大見出しがあればそれを題にし、無ければ「はじめに」とする。見出しが 1 つも無い返事は「本文」の 1 節である。
  - 要約は、見出しとコードブロックを除いた最初の段落である。
  - 文章の無い返事（理由の無い失敗など）と、サーバーが決める状態（待ちの上限切れ、相手が Task を覚えていない、相手が設定から外れた）は、サーバーの言葉の要約だけで、節を持たない。
- 取らなかった画像の書き方: 返事の `README.md` の「画像」の節に、名前と理由を並べる。
- DataPart の入口: 共通の形を検証する関数だけを用意した。DataPart を求めるのは作業単位 4 である。
- 依頼もディレクトリに置く（PR のレビューでの本人の指摘で足した）
  - 本人の問いは「どの依頼の返事で `/sources` が変わったのか分かるか」だった。返事だけを置くと、同じ相手に 2 つ頼んだときに区別できない。
  - `ask_agent` を受けた時点で、依頼のディレクトリを作る。そこに `request.md`（頼んだ時刻、相手、種類、続きなら前のやり取りのディレクトリ、文面の全文）を置き、返事はどの state でも同じディレクトリに置く。場所と文面は `agent_tasks` に、相手ごとの直近の依頼の場所は `agent_contexts` に記録する（migration 26）。送れなかった依頼のディレクトリは消す。
  - `README.md` の先頭に「頼んだこと」（頼んだ時刻と文面の先頭 3 行、全文は `request.md`）を置く。
  - 1 つのディレクトリの中で state が変わることはない。頼むたびに新しいディレクトリを作るからである。聞き返しに答えると A2A の Task は同じまま続くが、その答えも 1 つの依頼としてディレクトリを作り、Task の場所を答えのディレクトリに移す。聞き返し（`input_required`）は前の依頼のディレクトリに、答えた後の返事は答えのディレクトリに入る。
  - `continue` の依頼の `request.md` には、続けた前の依頼のディレクトリを書く。サーバーが相手ごとの直近のやり取りから分かる。分からないとき（この版より前のやり取り）は、分からないと書く。
  - `ask_agent` の結果で、依頼のディレクトリの場所を伝える。ADR 0024 は、なつみがツールの引数に写す ID を出来事に載せないという決定である。この場所は、なつみが読むファイルの場所である。どのツールの引数にも写さず、サーバーが付けた日時と短い印でできていて、Task や context の ID を含まない。そのため ADR 0024 には当たらない。

### 作業単位 4 で決めたこと（DataPart を求め、検証して置く）

- 拡張の URI は `https://github.com/yuanying/fraction-agents/tree/main/docs/extensions/reply/v1`（fraction-agents の ADR 0015）。
  natsumi のコードの定数にし、設定にはしない。URI が名指す形が、natsumi の読む形そのものだからである。
- 拡張を名乗るかどうかは、相手の Agent Card の `capabilities.extensions` で見る。
  - 起動時に頼める相手の一覧を書くために読んだ Agent Card（[ADR 0036](0036-a-manual-to-read-and-a-limit-on-waiting.md)）を、そのまま使う。依頼のたびには読まない。
  - 起動時に読めなかった相手は、頼むときに読み直す。それでも読めなければ、ヘッダを付けずに頼む。依頼そのものは止めない。
  - 起動した後に相手が拡張を名乗り始めても、再起動までは知らない。一覧と同じ扱いである。
- 求め方は、SendMessage に service parameter `A2A-Extensions: <URI>` を付ける（JSON-RPC では HTTP ヘッダ）。
  `@a2a-js/sdk` の `RequestOptions.serviceParameters` と `withA2AExtensions` で付けられた。fetch の差し替えは要らなかった。
  - 聞き返しへの答えにも付ける。fraction-agents は、Task を始めた要求か答えのどちらかで有効になっていれば返事に付ける。
  - `acceptedOutputModes` には `application/json` も足す。有効にするのは URI であり、これは添えるだけである。
- GetTask にはヘッダを付けない。返事の artifact は Task が済んだときに作られて Task に残り、GetTask はそれを返す。
  fraction-agents のコードと、実物のホスト（fake pi）に natsumi のクライアントで頼んで確かめた。
- 読むのは、済んだ Task の artifact のうち `extensions` に URI のあるものの、`mediaType` が `application/json` の DataPart だけである。
  ほかの DataPart は今までどおり読まない。
- 検証は JSON Schema（`reply.schema.json`）のとおりに厳しくする。欄の外の欄、空の文字列、文字数と行数と件数の上限、題の改行、
  `http`・`https` 以外の URL を断る。文字数はコードポイントで数える。JSON Schema の検証器は入れず、同じ規則を手で書いた
  （fraction-agents の `pi-package/lib/reply.ts` と同じ規則）。
  - 緩くしない理由: 拡張を名乗る相手は取り決めを守るはずで、守れていない返事を推し量って読むより、文章の扱いに戻すほうが確かである。
    文章は、同じ返事を Markdown にしたものなので、なつみの読む形はほぼ変わらない。
  - fraction-agents のホストは、取り決めに合わない返事をそもそも DataPart にしない（実物で確かめた）。natsumi の検証は、相手の不具合への備えである。
- 合えば、DataPart の要約・節・出典をそのまま置く。節の本文の中に見出しがあっても、節は切れない。
  合わなければ、今どおり文章を見出しで節に切る。
- どちらで置いたかは `result.json` に残す。中身は `form`（`data` か `text`）、置いた返事（`reply`）、
  DataPart が届いたときはその中身そのまま（`data`、合わなかったものも）である。
  `README.md` には書かない。なつみには、どちらの形で届いたかは要らない。
  - 合わなかったときは、サーバーのログに相手の名前と、合わなかった理由（欄の名前と規則）を 1 行出す。返事の中身は出さない。
    Consequences の「相手の側の不具合に気づきにくい」への手当てである。

## Consequences

- 長い返事でも、出来事に載るのは要約と場所だけになる。なつみは要約で足りなければ、`README.md` と必要な節だけを読む。文脈に入る量は、読んだ分だけになる。
- 読んだ節は `read` の結果として session に入り、畳み込みでも残る（ADR 0047）。全部の節を読めば、今と同じだけ文脈を使う。
- 返事のターンで、詳細が要るときは `read` を 1 回以上使う。要約で足りるときは 1 回も使わない。
- 返事は `/sources` に残り、作業環境からは読み取り専用で、なつみには消せない。data directory は返事の分だけ増え続ける。
- 画像は `/sources` と写しの 2 か所に残る。
- `attention` はすぐ出るので、返事は今と同じく取りに行く間隔の分だけ遅れて届く。awake hours の外でも出る（ADR 0050）。
- system prompt の出来事の説明と、`ask_agent` のツールの説明が変わる。反映した時点で prefix が変わる。
- DataPart に対応していない相手の返事は、見出しで切るだけなので、節の分け方は相手の書き方に左右される。
- 取り決めの拡張を名乗るのに中身が合わない相手の返事は、文章の扱いに戻る。なつみからは違いが見えないので、相手の側の不具合に気づきにくい。
  サーバーのログと `result.json` には残る（作業単位 4）。
