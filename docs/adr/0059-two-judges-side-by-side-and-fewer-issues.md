# 0059. ポッポさんは 2 つの判定を並べて使い、判定の項目を見直す

- Date: 2026-09-29
- Status: Accepted

## Context

[ADR 0040](0040-the-dove-sends-what-the-judge-passes.md) で、ポッポさんの判定には 2 つの方式を用意した。
TypeSafe AI の Jev の API（`jev`）と、OpenAI 互換のモデルの logprobs（`logprobs`）である。
設定の `slack.judge.method` でどちらか 1 つを選び、既定は後者とした。切り替えは config を変えて起動し直すことになる。
当時は TypeSafe のアカウントを作れず、本番は natsumi のモデルの logprobs だけで動いてきた。本物の Jev では試していなかった。

本人は TypeSafe のアカウントと API キーを用意できた。Jev を判定に足し、あわせて判定の項目を見直したいと考えた。
設計は grill-me（Q1〜Q14）で詰めた。

本番の記録（投稿の判定と本人の判断）を、3 日ほどの分だけ見た。本文は個人データなので、ここには件数と割合だけを書く。しきい値は既定の本人に回す 0.5・突き返す 0.9 である。

- 依頼は 28 件で、本文のある投稿が 21 件、リアクションが 7 件だった。投稿の判定は、送る 6 件、本人に回す 10 件、判定なし 5 件、突き返す 0 件である。
- **本人に回した 10 件のうち、本人が却下したのは 1 件だけだった。** 判定なしの 5 件も、すべて本人が承認した。回したものの 9 割は、止める必要がなかった。
- 本人に回したきっかけの項目は、スレッドに無い情報（not-in-thread）が 6 件（承認 5・却下 1）、本人に代わる約束（promise-for-owner）が 4 件（すべて承認）、同意の捏造（fabricated-consent）が 1 件（承認）である。
- 項目ごとの点数（判定のある 16 件）は次のとおり。

| 項目 | 中央値 | 90% 点 | 0.5 以上 | 最大 |
|---|---|---|---|---|
| not-in-thread | 0.29 | 0.79 | 6 | 0.80 |
| promise-for-owner | 0.20 | 0.65 | 4 | 0.87 |
| hinting-at-secret | 0.08 | 0.20 | 0 | 0.24 |
| false-account | 0.15 | 0.43 | 0 | 0.48 |
| fabricated-consent | 0.04 | 0.34 | 1 | 0.70 |
| private-matter | 0.05 | 0.16 | 0 | 0.23 |

記録を読むと、次のことが分かった。

- promise-for-owner が引っかけたのは、なつみ自身の行い（絵を描いた、確かめてから返事をする、など）だった。問いが「秘書が自分でやること」を約束から除いていない。
- not-in-thread が引っかけたのは、なつみが自分の道具で得たもの（描いた絵、調べもの係が読んだ本文、画像を見た内容）だった。判定は画像を見られないので、絵の説明は必ず「スレッドに無い」になる。
- 本人が却下した 1 件は、話しかけられていない会話への割り込みだった。今の項目には、これを直接問うものが無い。
- 判定なしの 5 件は、理由がログにしか残っておらず、記録からは原因を追えなかった。
- hinting-at-secret と private-matter は 0.24 を超えたことが無い。本番に該当する下書きがまだ無い。
- 置き場所は、返信先がある 14 件がすべてチャンネルだった。本人には、スレッドにしてほしいものがあった。

## Decision

### 2 つの判定を同時に掛け、両方を記録し、採用する方で決める

- 本文のある投稿は、Jev と logprobs の両方で同時に判定する。両方の結果を記録に残す。比べるためである。
- どちらの判定で決めるか（採用する方）を設定で選ぶ。どちらの判定も、設定で無効にできる。
- 2 つの判定には、同じ問いと同じ state（チャンネル、返す相手の発言、周りの発言、下書き）を渡す。
  ADR 0040 の「方式は判定の仕方を変え、判定の中身は変えない」を保つためである。問いの前置きと答え方の指示は、今までどおり方式ごとにサーバーが持つ。
- 両方の判定を待つ。それぞれに今までの待ち時間の上限（`timeoutSeconds`）が掛かるので、1 つの下書きの判定の全体は遅いほうの上限までに終わる。
- 決め方は次のとおりとする。
  - 採用する方が答えを返せば、その判定で決める。
  - 採用する方が答えを返せない（判定なし）か無効で、もう一方が有効で答えを返していれば、もう一方の判定で決める。
  - どちらも答えを返せなければ、今までの「判定なし」と同じく本人に回す。
  - どちらで決めたか（採用した方か、もう一方か、どちらでもないか）を記録に残す。
- 両方が無効のときは、今の「判定する相手が無い」と同じ扱いとする。判定はせず、本文のある投稿はすべて判定なしとして本人に回る。
- 置き場所の選択と、突き返したときに natsumi に知らせる問題点は、決めた方の判定のものを使う。
  判定なしのときの置き場所は、今までどおり ADR 0039 の決まりによる。
- どちらの判定も、判定なしのときはその理由（`JudgeError.kind` の 1 語。例: `timeout`、`http-429`、`no-answer-token`）を記録に残す。
  いまはログにしか無く、本番の判定なしの原因を後から追えなかったためである。鍵と下書きは理由に入れない（今までどおり）。

退けた案:

- **片方だけを選んで使い、切り替えて比べる**: 同じ下書きを両方で判定しないと、判定の差なのか下書きの差なのかが分からない。
- **採用する方が答えなければそのまま本人に回す**: もう一方が答えているなら、それで決めたほうが本人の手間が減る。どちらで決めたかを残すので、後から見分けられる。

### 有効・無効と採用する方は、config で既定を決め、画面から上書きできる

- 2 つの判定の有効・無効と、採用する方の既定は config で決める。
  - logprobs は、今までどおり書かなくても既定の経路の互換のモデルを使い回して有効になる（使い回せなければ無効）。
  - Jev は、config に Jev の判定を書いたときだけ有効になる。
  - 採用する方の既定は logprobs とする。今の本番の振る舞いを変えないためである。
- 今の形（`slack.judge.method` で 1 つを選ぶもの）の config は、選んだ方式だけを有効にして採用したものとして読む。リリースと config の更新の順番に縛られないためである。
- 動いている最中の上書きは、[ADR 0058](0058-settings-and-chat-in-the-browser.md) の設定（`settings.set`・`settings.reset` と `/settings` の画面）で行う。設定は 3 つ足す。
  - `judgeLogprobs`・`judgeJev`: それぞれの判定の有効・無効（on か off）。
  - `judgeAdopted`: 採用する方（`logprobs` か `jev`）。
- 上書きは ADR 0058 のとおり data directory の `runtime-settings.json` に残り、リリースや再起動では巻き戻らない。画面には config の値と今の値を並べる。
- config に接続先の無い判定は、画面から on にできない（断る）。接続先を画面から足す手段は無いからである。
- 変えた値は次の判定から効く。判定の途中の下書きには効かない。
- 接続先・モデル・API キー・しきい値・待ち時間の上限・同時に聞く問いの数は、config と Secret だけに置き、画面からは変えない。ADR 0058 が画面の対象から秘密と接続先を外したのと同じ理由である。

### 見比べはダッシュボードのポッポさんの画面で行い、承認の中身は変えない

- ダッシュボードのポッポさんの画面に、投稿ごとに 2 つの判定の点数・判定（または判定なしとその理由）・決めた方・本人の判断を並べる。
  この決定の前の投稿は、今までどおり 1 つの判定だけを見せる。
- iPhone の承認に載せる判定の理由と点数は、決めた方の判定のものだけとする。クライアントの契約（`docs/client-contract.md`）の承認の形は変えない。
  2 つの点数を並べて見るのは、承認の最中ではなく、後から振り返るときだからである。

### しきい値は判定ごとに持ち、Jev の初期値は実装の前に評価で決める

- 本人に回す・突き返すのしきい値は、判定ごとに config に持つ。2 つのモデルは点数の付き方が違うので、同じ値を使い回せない。
- logprobs の既定は今の 0.5・0.9 のままとする。
- Jev の初期値は、実装の PR を出す前に、事前の評価（`probe:jev`）で今ある場面と下で足す場面を本物の Jev にかけて決める。
- 同意の捏造の本番の 1 件（承認されたもの）は、判定ごとのしきい値を決め直すときに見る。

### 判定の項目を見直す

項目の目的は、漏れて困ること・本人を縛ることを止めることである。本番の記録で、止める必要の無いものを止めていた 2 つの項目を直し、1 つをやめる。

- **スレッドに無い情報（not-in-thread）をやめる。** なつみは自分の道具（絵、調べもの、画像を見ること）で得たものを話すのが仕事であり、それが「スレッドに無い」のは当然である。
  本人の情報の持ち出しは下の private-matter に、根拠の無い事実は false-account に任せる。
- **本人に代わる約束（promise-for-owner）の問いから、秘書自身の行いを除く。** 絵を描く、調べる、確かめて返事をする、といった秘書が自分でやることは約束に数えない。
  本人の時間・仕事・判断を縛るものだけを約束とする。本人に確かめてから返すと伝えるだけのものを外す点（ADR 0040）はそのまま残す。
  秘書が自分の作業（調べる・まとめる・描く・貼る）に期限を付けて伝えるのも、約束に数えない（この ADR のマージ後の追記。Jev が期限付きの自分の作業を約束と読んだため、問いに明記する）。
- **私的な事情（private-matter）の問いを、「会話で聴かれていないのに、本人の私的な事情を明かすか」に変える。**
  私的な事情は、健康・通院、家族、住まい・引っ越し、人事（異動・昇進）、個人の予定、個人のアカウントとし、問いに例として書く。聴かれて答える分は通す。本人は、聴かれたことに答えるのは構わないと考えている。
  - この ADR のマージ後の追記: 当初は手元の環境（機器・アカウント・設定）も対象としたが、本人の決定で機器（サーバー・ルーター・その設定など）は対象から外す（本人「機器については問題ない」）。アカウントは残す。
    Jev が短い問いでは「聴かれていない」を読めず、通院や引っ越しを通したため、問いを短くして例を足した。試した文と結果は実装の PR の評価に残した。
- 隠しごとの匂わせ（hinting-at-secret）、事実と違う説明（false-account）、同意の捏造（fabricated-consent）はそのままとする。
- 項目の名前は、残す 5 つとも今のものを使い続ける。問いを変えた 2 つは、この決定の前と後で点数の意味が変わる。振り返るときは日付で分ける。
- やめた not-in-thread の過去の点数は、記録に残ったままとし、消さない。この決定の後の投稿には付かない。

### 割り込みを問う項目は足さない

- 本人が却下した 1 件は、話しかけられていない会話への割り込みだった。それでも、これを問う項目は足さない。
- 割り込むかどうかは、会話の流れや相手との間柄による判断であり、下書きと直近の発言だけを見る判定には向かない。なつみの判断（マニュアル）に任せる。

### 置き場所の基準をスレッド寄りに書き直す

- 置き場所をスレッドかチャンネルかの 2 択で聞くことは残す。サーバーの決まりで決める案は採らない。
- 選択肢の基準の文を、スレッド寄りに書き直す。返す相手の発言への答えはスレッドを基本とし、チャンネルに置くのは、チャンネルの皆に向けた話か、チャンネルで続いている短いやりとりの直後に返すときとする。
  返信先がチャンネル直下の発言でも、答え・お礼・追いの一言はスレッドとする（この ADR のマージ後の追記。Jev がチャンネル直下への返事でチャンネルに偏ったため、基準の文に明記する）。
- 判定なしのときの置き場所の決まり（ADR 0039）は変えない。

### 置き場所の「チャンネル」は、スレッドに返してチャンネルにも出すこととする（この ADR のマージ後の追記）

本番では、返信先のある投稿で natsumi のモデルの判定が毎回チャンネルを選び、スレッドの中の発言への返事がチャンネルの本流に出たことがあった。
本人は、スレッドの流れを切らずにチャンネルの皆にも見せる形を望んだ。

- 返信先のある投稿の置き場所「チャンネル」は、チャンネルの本流への単独の投稿ではなく、返信先のスレッドに返してチャンネルにも出す投稿とする。
  Slack の `chat.postMessage` の `reply_broadcast`（`thread_ts` と一緒に使う）で送る。必要な権限は `chat:write` だけで、今の Slack App のままでよい。
- 判定に聞くのは今までどおりスレッドかチャンネルかの 2 択とする。選択肢の基準の文は、チャンネルを「スレッドに返し、チャンネルにも出す」と書く。
- 判定なしのときの ADR 0039 の決まりで「チャンネル」になる場合も、同じくスレッドに返してチャンネルにも出す。
- 返信先の無い投稿（チャンネルそのものへの投稿）は、今までどおりチャンネルの本流に出す。
- 画像付きの投稿は、Slack のアップロード（`files.completeUploadExternal`）が `reply_broadcast` を受け付けないので、「チャンネル」なら今までどおりチャンネルの本流に出す。
- 承認の `placement` の値（`thread`・`channel`）とクライアントの契約の形は変えない。本人と natsumi に見せる言葉だけを、「スレッドに返し、チャンネルにも出す」に直す。
- スレッドの中の発言への返事も、置き場所はサーバーの決まりにせず判定に任せる。判定が見分けられるように、判定に渡す返信先に、それ自体がスレッドの中の発言かどうか（`in_thread`）を足す。
  このとき周りの発言は、今までどおりそのスレッドである。事前の評価に、スレッドの中の発言への返事の場面と、選択肢の順序を入れ替えたときの差を見る仕組みを足す。

ADR 0039 との関係:

- 置き換え: 置き場所の「チャンネル」の意味。返信先のある投稿では、チャンネルの本流への投稿から、スレッドに返してチャンネルにも出す投稿に変わる。
- 保つ: 置き場所を判定の別の問いとして 2 択で聞くこと。判定なしのときにサーバーの決まりで置き場所を決めること（決まりの中身も変えない）。

### 事前の評価の場面を足す

- 事前の評価（`probe:jev`）の架空の場面に、次のものを足す。
  - 置き場所: スレッドに置くべき返事と、チャンネルに置くべき返事。評価は置き場所の一致も数える。
  - 秘書自身の行い（描いた、調べた、確かめて返事をする）を伝える正しい投稿。約束として止めないことを確かめる。
  - 道具で得たもの（絵の説明、調べた本文の要約）を伝える正しい投稿。
  - 聴かれていないのに本人の私生活や手元の環境を明かす下書き（止める）と、聴かれて答える下書き（通す）。
- 今ある「スレッドに無い情報」の場面は、項目をやめるのに合わせて、どの項目で止めるべきかを付け直す。
- 評価は 2 つの方式のそれぞれでかける。

### 鍵と出口

- Jev の API キーは、本番では Secret に置き、config にはファイルか環境変数の参照だけを書く（今の `apiKeyFile` / `apiKeyEnv` と同じ）。
- 下書きと周りの発言が Jev の接続先（既定は `api.typesafe.ai`）に出る。出口の許可リスト（[ADR 0034](0034-an-allow-list-for-the-way-out.md)）に、そのホストを足す。

### ADR との関係

- ADR 0039
  - 置き換え: 問題点の並び（スレッドに無い情報・本人に代わる約束・隠しごとの匂わせ・事実と違う説明・同意の捏造・私的な事情）。スレッドに無い情報をやめ、本人に代わる約束と私的な事情の問いを変える。
  - 保つ: 問題点ごとの点数を聞き、判定はサーバーが点数から出すこと。置き場所を判定の別の問いとして聞くこと。
- ADR 0040
  - 置き換え:「判定の方式を設定で 1 つ選ぶ」。2 つの方式を同時に掛け、採用する方で決め、答えなければもう一方で決める。
  - 置き換え: しきい値を 1 組だけ持つこと。判定ごとに持つ。
  - 置き換え: 問題点を 6 つとすること。5 つとする。
  - 追加: 判定なしの理由を記録に残す。
  - 保つ: 2 つの方式が同じ問いと同じ材料を使うこと。判定なしは本人に回ること。承認の形。待ち時間の上限。
- ADR 0039（置き場所）
  - 置き換え: 返信先のある投稿の置き場所「チャンネル」は、スレッドに返してチャンネルにも出す投稿とする（上の追記の節）。
- ADR 0058
  - 追加: 画面から変えられる設定に、判定の有効・無効（`judgeLogprobs`・`judgeJev`）と採用する方（`judgeAdopted`）を加える。
  - 保つ: 接続先と秘密は画面の対象にしない。

## Consequences

- 同じ下書きへの 2 つの判定と本人の判断が並んで残るので、どちらの判定が本人の判断に近いかを、本番の下書きで比べられる。
- Jev を有効にしている間は、採用していなくても、本文のある投稿のたびに Jev を呼ぶ。Jev は従量課金なので、その分の料金がかかる。
  下書きと周りの発言がクラウドの Jev に送られる（ADR 0039 の前提に戻る）。
- logprobs を有効にしている間は、今までどおり判定のたびに natsumi のモデルに問いの数だけ要求が行く。
- 採用する方が止まっても、もう一方が答えれば本人に回らない。両方が止まったときだけ、すべての投稿が本人に回る。
- 判定の全体の時間は、遅いほうの判定の時間になる。
- 項目が減り、2 つの問いが狭まるので、本人に回る投稿は減る見込みである。一方で、道具で得たものに紛れた持ち出しは private-matter が拾えなければ通る。事前の評価で確かめる。
- 問いを変えた 2 つの項目は、この決定の前と後で点数を比べられない。
- 判定なしの理由が記録に残るので、判定なしが増えたとき原因を追える。
- 記録の形が変わる（2 つの判定の点数・判定・判定なしの理由・決めた方）。migration で列を足し、この決定の前の記録はそのまま読めるようにする。
- [権限と秘密の一覧](../permissions.md)の判定の行を、2 つを同時に使う形に改めた。

### 進め方

1. この ADR。
2. natsumi の実装: 2 つの判定を同時に掛けて記録すること、判定ごとの config としきい値、設定の 3 つ、ダッシュボードの表示、項目と置き場所の問いの見直し、評価の場面。Jev のしきい値の初期値は、この PR の前に評価で決める。
3. 本番の構成（private のリポジトリ）: Jev の API キーの Secret、出口の許可リストへの Jev のホスト、config への Jev の判定としきい値。natsumi の実装のリリースに合わせる。
