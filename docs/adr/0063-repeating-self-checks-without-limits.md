# 0063. 自分で予約する確認を cron 式で繰り返せるようにし、上限をなくす

- Date: 2026-09-30
- Status: Accepted

## Context

[ADR 0014](0014-self-checks-and-pings.md) で、natsumi は `schedule_self_check` で後で自分から確かめる予約を入れられるようになった。
予約は一回きりで、`in_minutes`（何分後）か `at`（本人のタイムゾーンの時刻）で書く。
暴走を心配して、サーバーが次の制限を掛けていた。

- 最短の先（既定 5 分）と、最も遠い先（既定 7 日）
- 同時に待たせる件数（既定 5 件）と、1 日に予約できる件数（既定 20 件。取り消したものも数える）
- 同じ理由の予約が待っていれば、新しく作らず 1 件にまとめる

本人は、予約を次のように使いたいと考えた。

- 「毎日 16 時」「10 分ごと」のような繰り返し。一回きりの予約を毎回入れ直すのでは、入れ忘れると止まる。
- 「9/2 の 18 時」のような、7 日より先の一回きり。
- 繰り返しと一回きりを、同じ理由で持つこと。今の「同じ理由はまとめる」では、後から入れた方が消える。

これまでの運用では、制限に当たったのは本人に頼まれた正当な予約の方だった。
暴走したときは、予約を本人が見て消せれば足りる（ダッシュボードの一覧と削除は別の変更で足す）。

設計は grill-me（Q1〜Q5）で詰めた。

## Decision

### 書き方

ツールの名前は変えない。`schedule_self_check` に `cron` を足し、`cron`・`at`・`in_minutes` のどれか 1 つだけを書く。

| 引数 | 予約 | 書き方 |
|---|---|---|
| `cron` | 繰り返し | 5 項目の cron 式（分 時 日 月 曜日）。例: `0 16 * * *`（毎日 16:00）、`*/10 * * * *`（10 分ごと） |
| `at` | 一回きり | 今までどおり。本人のタイムゾーンの `HH:MM` か `YYYY-MM-DD HH:MM` |
| `in_minutes` | 一回きり | 今までどおり。今から何分後か（1 以上の整数） |

- 一回きりを cron で書くと、翌年も同じ日に繰り返す。だから一回きりには `at` を残し、cron とは分ける。
- cron 式は本人のタイムゾーン（`loop.timeZone`）で読む。夏時間で存在しない時刻は、その回が無いものとして次の回に進む。
- 読むのは数字・`*`・範囲（`1-5`）・リスト（`1,15`）・間隔（`*/10`、`0-30/15`）である。曜日は 0 と 7 が日曜日。
  月や曜日の名前（`MON`）と、`@daily` などの別名は読まない。
- 日と曜日の両方を指定したときは、どちらかが合えば動く。一般的な cron（Vixie cron）と同じである。
- 次の場合は予約せず、読める文で理由を返す（エラーの結果にする）。思考ループは止めない。
  - 項目の数が違う、範囲の外の数、読めない書き方、間隔が 0、範囲が逆
  - 当てはまる時刻が一度も来ない式（`0 0 30 2 *` など）
  - どの回も起きている時間帯の外にあり、一度も届かない式
- 成功の結果には、cron 式と、次に届く時刻（起きている時間帯の中の最初の回）を書く。

### 上限をなくす

- 最短の先・最も遠い先・同時に待たせる件数・1 日の件数の 4 つをすべてなくす。下限は cron の 1 分である。
- 同じ理由の予約を 1 件にまとめる処理もなくす。同じ理由で、繰り返しと一回きりを別々に持てる。
- `loop.selfCheck` の設定もなくす。本番の設定ファイルに残っていても起動は止めない。
  読まない設定として起動時のログに出す（Slack の古い設定と同じ扱い。[ADR 0050](0050-telling-of-source-updates-with-one-event.md)）。

### 起きている時間帯と、止まっていた間

- 一回きりの予約は今までどおりである。夜に時刻が来たら朝に届き、止まっていた間に過ぎたものは起動後に届く。
  どちらも遅れた分数（`late_minutes`）が付く。
- 繰り返しの予約は、時刻の来た回をためない。時計を見たとき、直近の回を 1 回だけ届けるか、飛ばすかを決める。
  - 直近の回が起きている時間帯の中にあり、今の「起きている時間」が始まってから（今日の 8:00 以降など）の回なら届ける。
  - そうでなければ飛ばす。時間帯の外の回（夜の回）と、夜をはさんで取り残された回がこれに当たる。
  - 朝は、起きている時間帯が始まった後の最初の回から届く。
  - 処理中のターンが長引いた、サーバーが止まっていた、などで何回分かを過ぎても、届くのは直近の 1 回だけで、遅れた分数が付く。
    止まっていた間の回を飛ばす案もあった。まとめて 1 回にしたのは、「10 分ごと」の予約が再起動のたびに 1 回抜けるより、
    遅れても 1 回届く方が、natsumi が自分の予定を追いやすいからである。夜をまたいだ分は、上のとおり飛ばす。
- 保存する「次の時刻」は、そのときの起きている時間帯の中の次の回にする。一覧とダッシュボードには、実際に届く時刻が出る。
  起きている時間帯は動作中に変わりうる（[ADR 0058](0058-settings-and-chat-in-the-browser.md)）ので、届けるときにも時間帯を確かめ直す。

### 届け方

- イベントは今と同じ `self_check` で、時刻の来た予約を何件でも 1 件にまとめる。
- `checks` の各項目に check_id・理由・予定の時刻（`scheduled_for`）を載せる。繰り返しの予約には `cron` を添える。
  どの予約か、繰り返しかが、イベントから分かる。
- 繰り返しの予約は、届けても待っている状態のまま、次の時刻へ進む。取り消すまで続く。
- 予約とイベントは、今までどおり同じ transaction で記録する。同じ回を二度渡さない。

### 一覧と取り消し

- `list_self_checks` は、繰り返しの予約に cron 式と次の時刻を添える。
- `cancel_self_check`（check_id）はそのままで、繰り返しの予約も取り消せる。

### cron 式を自前で読む

ライブラリを使わず、サーバーの中で読む。

- 読むのは 5 項目の数字と記号だけで、小さい。
- 時刻の計算は、本人のタイムゾーンの壁時計で行う必要がある。サーバーには、夜の切り替え（ADR 0009）と予約で使っている
  タイムゾーンの変換がすでにあり、同じものを使える。夏時間の扱いもそろう。
- 依存を増やさない。公開のリポジトリで、版の固定とライセンスの確認を続ける手間がかからない。

### 記録

SQLite の migration version 25 で、予約の表を作り直す。

- 予約に cron 式の列を足す。一回きりは空で、繰り返しは届いた状態にならない。
- 同じ理由をまとめるための列と一意の制約、1 日の件数を数えるための索引をなくす。
- どのイベントがどの予約のどの回を運んだかを、別の表に持つ。繰り返しの予約は多くのイベントに運ばれるからである。
- 待っている予約は、一回きりとしてそのまま残る。届いた予約は、運んだイベントを新しい表に移す。

### 置き換える既存の決定

- ADR 0014
  - 置き換え: 予約の上限（最短の先・最も遠い先・同時の件数・1 日の件数）と、同じ理由をまとめる処理。どちらもなくす。
  - 置き換え: 設定 `loop.selfCheck`。なくす。
  - 追加: `schedule_self_check` の `cron`、繰り返しの予約、繰り返しの時間帯の外の回を飛ばすこと。
  - 残す: 一回きりの予約の書き方と届き方、1 件のイベントにまとめること、ループが静かなときだけ入れること。

## Consequences

- 本人に頼まれた予約が、件数や先の遠さで断られることはなくなる。
- 一方、サーバーは予約の暴走を止めない。natsumi が「1 分ごと」の予約を入れると、起きている時間帯のあいだ、
  ターンが空くたびにモデルを使い続ける。止めるのは本人である（`cancel_self_check` を頼むか、ダッシュボードで消す）。
- ツールの定義と system prompt が変わるので、prefix のキャッシュは、次の夜の切り替えで session が作り直されるまで効かない。
- 夜にだけ動く繰り返しの予約は入れられない。夜中に本人へ声をかける用途には、今までどおり使えない。
- 繰り返しの予約は、止まっていた間や長いターンの間の回を 1 回にまとめる。何回分が過ぎたかは natsumi に伝わらない。
- schema 25 に上げた後、古い版のサーバーは起動を拒む（知らない schema の版）。戻すときは、上げる前のバックアップの
  `.natsumi/state.sqlite` に戻す。
